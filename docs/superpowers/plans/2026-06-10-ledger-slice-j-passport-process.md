# Ledger slice J — Nepal passport process readiness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Enrich the *existing* "Passport bio page" checklist row with a conditional how-to-start note (shown only when no passport is uploaded) and add one `hasPassport`-gated plan action `start-passport-process` carrying the e-passport pre-enrolment process — wire A.043–A.046; reuse A.049 (central-office ~2 working days) read-only — without adding any new document kind, scoring, or `VISA_PREP_KINDS` change.

**Architecture:** New 4-record sourced module `lib/data/source/nepal-passport-process.ts` (no `kind` discriminator — records picked by `id`, mirroring the multi-record shape) + Zod schema + one registry line. The checklist generator makes the existing passport `add()` conditionally carry a soft note + SourceLine when the passport is not uploaded; the plan generator gains `hasPassport?: boolean` and emits `start-passport-process` only when `hasPassport === false`. `lib/plan/invalidate.ts` (the sole production caller of `generatePlan`) loads the user's uploaded document kinds via `listDocumentsForUser` and derives the boolean — the plan's only new input, kept narrow. Slice-kit flips the 4 new findings to `used` via `FLIP_STATUS`. No scoring code touched; no new checklist item; no new `DocumentKind`; no `phases.ts` edit.

**Tech Stack:** TypeScript (strict, `noUncheckedIndexedAccess`), Zod, vitest. Git via the Bash tool (for `node` heredocs and the `FLIP_STATUS=1` env var). Branch `ledger-slice-j-passport-process` (already created; spec committed `9ba047c`).

**Spec:** `docs/superpowers/specs/2026-06-10-ledger-slice-j-passport-process-design.md` (approved 2026-06-10 — Option B: checklist note + gated plan action).

**Copy + scope constraints (user, locked at approval):**
- **Conditional framing:** the checklist note opens "If you still need a passport, …" — never assert non-possession ("you don't have a passport"). Upload status ≠ possession.
- **Narrow input:** `invalidatePlan` loads only uploaded document **kinds**; the generator gains only `hasPassport?: boolean`. No broad documents-table dependency.
- **Omitted ⇒ not emitted:** the action gates on `inputs.hasPassport === false` (strict), so older/direct test callers that omit `hasPassport` (undefined) get no passport action.
- **Plan title** is "Start your passport application" (verbatim). **Fees not wired** (A.047/A.048 stay in `nepal-application-fees`/cost-to-apply). **A.050 use-later** (district 15–45 days range). Destination-agnostic → **not** in `VISA_PREP_KINDS`.

```ts
import { z } from "zod";
import { ProvenanceSchema, HttpUrl, IsoDate } from "./common";

/**
 * Runtime schema for lib/data/source/nepal-passport-process.ts. Guards the id enum
 * (no kind discriminator), non-empty label/summary, the http(s) source, ISO lastVerified,
 * unique ids, and provenance (>=1 findingRef).
 */
const NepalPassportProcessRecordSchema = z.object({
  id: z.enum(["pre-enrolment", "choose-centre", "barcode-copy", "enrolment-biometrics"]),
  label: z.string().min(1),
  summary: z.string().min(1),
  source: HttpUrl,
  lastVerified: IsoDate.optional(),
  provenance: ProvenanceSchema,
});

export const NepalPassportProcessSchema = z
  .array(NepalPassportProcessRecordSchema)
  .refine((rows) => new Set(rows.map((r) => r.id)).size === rows.length, {
    message: "Nepal passport-process ids must be unique",
  });
```
