## What this is

The fourth jsdom-blind slice: **stop reading `window` / the wall clock in component
render bodies** on the anonymous assess → results trust paths. Each of these produces
a server-vs-client hydration mismatch that a green 1897-test jsdom suite cannot catch
(jsdom has no SSR→hydrate diff, no timezone divergence). One of them (#4) also hides a
real **trust bug**: the assessment expiry is computed from the live clock at *view*
time, so the recovery route always shows "3 days from now" regardless of the
assessment's real age.

**Hard constraint:** do not regress **[MV-28](MV-28-anon-results-recovery.md)** — the
anonymous "refresh on results" recovery path must still restore results from
`sessionStorage`. The fix changes *when* the restore happens (after mount, so SSR
output is stable), never *whether* it happens.

## Findings in this slice

### #3 — `components/assess/assess-flow.tsx` (`readPersistedResults()` in render)
`readPersistedResults()` reads `window.sessionStorage` **in the render body** to seed
`useState(phase)`. SSR → `phase='wizard'`; client first render (sessionStorage has
results) → `phase='results'` = whole-subtree hydration mismatch + a visible wizard
flash, exactly on the MV-28 recovery path.
**Fix:** render the SSR / first-client shell identically (stable initial phase), then
restore the persisted phase in a mount `useEffect` (or `useSyncExternalStore` with a
`getServerSnapshot` that returns the stable value). No `window` read during render.

### #7 — `components/wizard/use-wizard-state.ts` (`readPersistedWizard()` in render)
Same pattern: `readPersistedWizard()` in the render body seeds `useState(profile/index)`
→ step-1 flash. Folded into #3's fix (same mount-gate technique).

### #4 — `components/results/conversion-paths.tsx` (`expiryDate()` in render) + TRUST bug
`expiryDate()` reads `new Date()` and formats month/day **in render** on the SSR
`/assessment/[id]` route → server (UTC) vs client (Asia/Kathmandu UTC+5:45) timezone
mismatch. **Adjacent trust bug on the same line:** expiry is derived from `new Date()`
at view time, not the assessment's stored creation timestamp → the route always shows
"3 days from now" no matter the assessment's real age.
**Fix:** derive expiry from the **stored creation timestamp** (creation + 3-day product
window), computed **server-side** and threaded through the payload/props as an absolute
value; render it without reading the clock. (3-day expiry is a product constant — see
CLAUDE.md "Assessment expiry: 3 days".)

### #11 — `components/results/intake-timing.tsx` (`buildIntakeTimeline` default `now`)
`buildIntakeTimeline(intake)` (`lib/timing/intake.ts`) defaults `now=new Date()` → the
inline `left:%` (offsetPct) differs SSR vs client (float mismatch). React 19 dev-only
`console.error`; the div is `aria-hidden`.
**Fix:** compute `offsetPct` **server-side** (thread an explicit `now`/offset via
props/payload so SSR and client agree).

## Approach

Each finding shares one root cause — impure render reading environment/time — and one
cure — move the impure read to the server (compute into the payload) or behind a mount
effect. The exact data-flow (where the creation timestamp lives, how each component
receives props) is confirmed by the mapping workflow before edits.

## Test plan (jsdom-visible contracts, RED-first)

- **#3/#7:** `renderToStaticMarkup(<AssessFlow …/>)` (and the wizard hook's SSR path)
  render the **stable pre-restore shell** regardless of `sessionStorage`; a mounted
  render then swaps to results — i.e. SSR markup is deterministic and independent of
  `window`. MV-28's existing recovery test stays green.
- **#4:** given a **fixed creation-timestamp prop**, the rendered expiry text is
  deterministic and equals creation + 3 days — **independent of the current time**
  (freeze/inject time; assert the string, proving the clock is no longer read in render).
- **#11:** `buildIntakeTimeline(intake, explicitNow)` returns a deterministic
  `offsetPct`; the component renders the passed offset (no `new Date()` in render).
