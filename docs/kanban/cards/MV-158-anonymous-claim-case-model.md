# MV-158 — Anonymous claim under the case model: create-or-resolve a personal case, dual-write owner + case_id atomically, every MV-130 / MV-135 leg preserved

**Priority:** P1   **Owner:** agent
**Goal:** Move the anonymous-assessment claim — the plan's named *hardest dual-write site* — onto the case model without losing one converting student's work: every claim create-or-resolves the claimer's personal case, binds `owner` **and** `case_id` in a single atomic statement, keeps at most one primary assessment under **both** the legacy owner-scoped and the new case-scoped unique predicates, and preserves MV-130's honest recovery states and MV-135's purge contract exactly — identically for Google OAuth, the emailed 6-digit code, the emailed link, and the signed-in recover-in-place endpoint.

**A · Personal-case resolution (runtime, idempotent, first)**
- [ ] **The claim path CONSUMES MV-157's resolver. This card adds no new resolver.** `lib/cases/personal-case.ts` is created by MV-157's commit on the same branch (criterion J below), exporting `resolvePersonalCaseId(actorUserId, db?)` and `ensurePersonalCase(sessionUser, db?)`, and already wiring `ensurePersonalCase` into the no-pending-claim branch of `lib/auth/finish-sign-in.ts`. The claim branch calls the same `ensurePersonalCase`. Writing a second create-or-resolve helper here — under any name — splits one invariant ("one personal case per student") across two implementations, which is exactly how two personal cases silently split one student's data.
- [ ] **`ensurePersonalCase` takes the verified Supabase `User` object and derives `display_name` / `email` INTERNALLY. It does NOT take a `{ displayName, email }` parameter.** Corrected 2026-08-02: an earlier draft of this criterion had this card *widen* `ensurePersonalCase(actorUserId, db?)` with an optional `{ displayName, email }` bag, while the test plan simultaneously required that "a caller-supplied name or email that did not come from the session" be ignored. **Those two cannot both be true.** Once the values arrive as plain strings the function has no way — none, at any layer — to tell a string the caller read off `supabase.auth.getUser()` from a string it read off a request body; the test could only ever assert the behaviour for the shapes the test author imagined, and the criterion would read as proven while being unprovable. The resolution is the one that makes the claim structural: the parameter is the **verified `User`** returned by `supabase.auth.getUser()` on the server, and the derivation happens inside the function. There is then no channel through which a client-supplied string can reach `cases.display_name` or `cases.email`, and "non-session values are ignored" is true by construction. Because MV-157 and MV-158 ship in one PR, this is the signature from MV-157's first commit — there is no widening step and no backward-compatibility obligation.
- [ ] **This card owns the derivation rules and their tests** (MV-157 owns resolution and idempotency). `display_name` precedence, computed inside the function from the `User`: `user_metadata.full_name` → `user_metadata.name` → the local-part of `user.email` → a stable non-empty fallback (`"MeroVisa student"`). `email` is `user.email`. Never `""`, never the literal `"undefined"`, never null — `cases.display_name` is `not null`.
- [ ] Resolution runs **before** any write to `assessments`. It is the one step allowed to fail without touching the student's row, which is what makes the new failure leg (criterion F4) honestly retryable.
- [ ] It is **idempotent and race-safe** — MV-157's property, re-asserted here because the claim path is the one that races: concurrent calls for the same `userId` return the same case id and never create a second one. It relies on MV-155's `cases_personal_student_idx` (partial unique on `cases (student_user_id) where organization_id is null`) and handles the unique-violation branch as a resolve, not an error. **If that index is not in the database, this card is blocked** — a read-then-insert without it is a lost update, and two personal cases silently split one student's data.
- [ ] **Google and email sessions produce the same value from the same available data** — the derivation reads the `User` object, not the provider, so there is no provider fork to drift. Tested: an email-OTP session carrying no `full_name` yields the email local-part, never an empty string and never the literal `"undefined"`.

**B · The atomic bind**
- [ ] `claimAssessment` sets `owner`, `case_id`, **and** `claimed_at` in **one** conditional `UPDATE`, retaining the existing guard `where id = ? and owner is null and expires_at > now()`. Two sequential updates are prohibited: a crash between them leaves an **owned-but-case-less** row that MV-157's case-scoped reads cannot see, so the student's own assessment disappears from their dashboard while the row sits in the table.
- [ ] The predicate is unchanged in strength — an already-claimed or expired row still matches nothing, so an authenticated caller supplying an arbitrary UUID to `/api/assess/claim` still cannot steal another account's assessment.
- [ ] A failed bind leaves **no** partial state on the assessment row. A personal case created moments earlier and then not used is acceptable and explicitly non-orphaning (the user needs it regardless, and it is a per-user singleton).

**C · Profile bootstrap on claim**
- [ ] The bootstrap dual-writes `owner` **and** `case_id`, and its "does a profile already exist" check is asked **per case** (MV-157's case-aware `getProfile`/`upsertProfile` signature), not per owner.
- [ ] During the dual-key window `profiles.owner` is still `unique`, so the upsert must not attempt a second profile row for the same Auth user. The bootstrap is a no-op when the row exists, exactly as today (`claim.ts:64-69`).
- [ ] A bootstrap failure does **not** fail the claim (the row is already bound and the student is already converted), and it is logged, never swallowed silently.

**D · Primary-assessment uniqueness — under both keys**
- [ ] After any claim, the claimer holds **exactly one** `is_primary` assessment, and it is the newest — the existing newest-wins contract.
- [ ] The demote step satisfies **both** live predicates while both exist: the legacy `assessments_primary_idx on (owner) where is_primary` and MV-155/MV-157's case-scoped equivalent. A demote scoped to `case_id` alone leaves a same-owner primary in another case, the promote then trips the legacy index, the error is logged rather than thrown, **and the dashboard stays pinned to the first assessment ever claimed** — the MV-16 regression that `tests/integration/claim-path.itest.ts` exists to catch.
- [ ] Demote-then-promote ordering is preserved (after the demote the key is free, so the promote cannot collide), and both statements' errors continue to be logged with enough context to diagnose which one failed.
- [ ] A test pins that the promote is **not** made unconditional or moved before the demote as a "simplification".

**E · Anonymous rows stay case-less, and the purge still works**
- [ ] `createAnonymousAssessment` continues to write `owner: null` **and** leaves `case_id` null. Pinned by a test, because MV-155's "anonymous assessments purge under MV-135's 3-day policy" only holds while they are case-less.
- [ ] `lib/assessments/purge.ts` keeps **`owner is null`** as its load-bearing predicate in both the scan and the delete. It is **not** re-keyed to `case_id is null`. A test proves an **owned assessment with a null `case_id`** — the exact residue of a partially-applied claim or of a row claimed in the MV-157→MV-158 window — **survives a purge run**. Re-keying on `case_id` would make that row deletable.
- [ ] A test proves an unclaimed, expired, case-less row is still purged, so the case work has not quietly stopped retention.
- [ ] **A claim token pointing at a purged row stays honest:** the conditional update matches nothing, `getAssessmentClaimState` returns `null`, and the seam renders `?error=expired` ("expired and was deleted") — never `claim-failed`, and never a blank page. Covered for a row purged *before* the claim and for one purged *between* personal-case resolution and the bind.

**F · Every MV-130 recovery leg, preserved and extended**
- [ ] **F1 `already-mine`** — a re-claim of the caller's own row still lands on `/assessment/{id}` as a success, with no re-bootstrap, no duplicate lead, and no second personal case.
- [ ] **F2 `already-mine` heals a case-less row** — when the row is owned by the caller but `case_id is null`, the re-claim **repairs it** (resolves the personal case, sets `case_id`) instead of merely landing the student on a row their case-scoped dashboard cannot render. This is the runtime remedy for rows claimed in the MV-157→MV-158 window; the bulk remedy is **MV-160 §B's reconciliation sweep**, which that card now carries as the first ordered step of its migration.
- [ ] **F3 `claimed`** — a row bound to another account still returns `claimed` → `/assess?error=claimed` (409 on the API). Classification still reads back through the admin client, because RLS would hide another owner's row.
- [ ] **F4 `error` — the NEW leg** — a failure of personal-case resolution (or of the bind's DB call) returns `reason: "error"` → `/assess?error=claim-failed` (503 on the API), never `expired`. The student's assessment is untouched and still claimable; telling them it is gone would be the exact dishonesty MV-130 was built to remove.
- [ ] **F5 `expired`** — purged / deleted / past-TTL is unchanged (410 on the API).
- [ ] The `ClaimFailureReason` union and the `lib/auth/claim-error.ts` code contract change only by addition; an unrecognised code still renders the normal flow.

**G · Provider parity — all four entry points, one path**
- [ ] **Google OAuth** (`app/auth/callback/route.ts:35`), **the emailed 6-digit code** (`app/api/auth/email/verify/route.ts:63`), and **the emailed link** (same callback) produce byte-identical results: same personal case, same `case_id` on the assessment, same landing path. - [ ] A test asserts that a session with **no** `full_name` (the email path) still yields a valid personal case.

**H · Concurrency**

- [ ] Two concurrent claims of **different** assessments by the same user yield exactly one primary — the winner of the demote/promote race — and never a swallowed unique violation that leaves zero primaries.

## Risk notes
- **The silent-loss failure mode is the whole card.** A row with `owner` set and `case_id` null is the worst outcome available here: no error is raised, no test fails by default, the student signed in successfully — and their assessment is simply not there. It is produced by a non-atomic bind, by a bootstrap that writes the profile before the case exists, or by shipping MV-157 without MV-158. Every criterion in section B exists to make that state unreachable, and F2 exists to heal it if it ever occurred.
- **The dual-key window is real and short-lived.** While `assessments_primary_idx on (owner)` and `profiles.owner unique` both survive, **one Auth user can hold at most one primary assessment and one profile across all cases**. Stage 2 is safe because owner ↔ personal case is 1:1. **It stops being safe the moment Stage 3 links an existing student to a consultancy case** — MV-160 must drop both legacy keys before that. Handed to MV-160 explicitly; do not drop them here (MV-158 ships no migration).
- **MV-135's landmine, restated because the case model invites exactly the wrong fix.** A claim never extends `expires_at`, so every converted student's row looks permanently expired. `owner is null` is the only thing that keeps the purge from deleting the rows of the students who signed up. Under the case model `case_id is null` *looks* like a cleaner predicate and selects the same set today — but it deletes any claimed row whose `case_id` write was lost. Do not re-key the purge. Two tests pin it.
- **A claim can race the purge in both directions.** Token issued → row purged → claim arrives is the common case and must render `expired`. Personal case resolved → row purged → bind arrives leaves a case with no assessment; harmless and idempotent, but the reason string must still be `expired`, not `error`.
- **This is live user data, and it is the first time the claim path writes a new copy of it.** `cases.display_name` and `cases.email` will hold real students' names and addresses. Same controller, same purpose, same data subject — not the staff-entered third-party data D-B gates — but it is a new table holding PII and it should be recorded as such in the Stage 2 reversibility log (MV-154) rather than noticed later.
- **Rollback is a revert, and the revert must be safe.** This card ships **application code, not a migration**, so it has no rehearsal obligation of its own — but the rows it writes at runtime (personal cases, `case_id` on assessments and profiles) survive a revert. Pre-MV-158 code ignores `case_id`, so the personal student experience keeps working on reverted code; the residue is additive and is reconciled by MV-160. State this in the PR body rather than leaving the integrator to infer it.
- **Service-role stays, and that is the correct answer here.** Plan lines 340–344 name "account linking" as a sanctioned exception, and it is structurally necessary: the row has no owner, so an authenticated client under RLS cannot see the row it is about to claim. The risk is scope creep — a future author reaching for the same admin client to do a case-scoped read "while we're here". The ESLint fence and the exception list's `requiredCaseCheck` field are what stop that; keep both accurate.
- **`googleName` is a Google-only name on a parameter three providers now use.** Renaming it to `displayName` is in-file and welcome; leaving it is a readability debt that will mislead the next author about provider parity. Not a blocker either way — record the choice.
- **Four entry points, one seam — keep it that way.** MV-147's cost was paid to make Google and email converge on `resolveSignInDestination`. Adding a case branch to one caller instead of to `claimAndBootstrapProfile` re-forks the path and the divergence will surface as "email users' assessments don't show up", weeks later.

## Decision log
- 2026-08-02 — Card carved from Stage 2 of the revised consultancy plan (integrator session).
- 2026-08-02 — **Carved out of MV-157 rather than left inside it**, because the plan singles this path out by name (line 329) and because its failure mode is silent: MV-157's other call sites fail loudly when `case_id` is missing, whereas a mis-claimed row looks like a successful sign-in and an empty dashboard. It also drives the only *runtime* create-or-resolve on a path that races — every other table's `case_id` arrives by backfill.
- 2026-08-02 — **Seam check: MV-157 owns the resolver; this card owns only the display-name/email derivation.** The first draft had this card writing `lib/cases/personal-case.ts` and `tests/cases/personal-case.test.ts` from scratch, exporting `resolvePersonalCase(db, { userId, displayName, email })` — a second create-or-resolve implementation of an invariant MV-157 already implements and already wires into `lib/auth/finish-sign-in.ts`. Two resolvers for "one personal case per student" is precisely the shape that produces two personal cases per student. Boundary: MV-157 owns resolution and idempotency; MV-158 owns derivation and the claim-path call.
- 2026-08-02 — **Integrator, post-Codex-review: `ensurePersonalCase` takes the verified `User` object; the `{ displayName, email }` widening is withdrawn.** The intermediate draft had this card widen `ensurePersonalCase(actorUserId, db?)` with an optional `{ displayName, email }` bag while its test plan simultaneously demanded that non-session values be ignored — **an unprovable pair**. Once identity arrives as two plain strings, no layer of the function can distinguish a value read off `supabase.auth.getUser()` from one read off a request body; the "ignored" test could only ever cover the shapes its author thought of, so the criterion would have read as proven while being unfalsifiable. Two fixes were available: narrow the claim (say only "the caller must pass session-derived values", and stop asserting enforcement), or pass the verified session object and derive internally. **The second was chosen** — it makes the claim structural rather than aspirational, and it costs nothing, because every call site already holds the `User` it got from `supabase.auth.getUser()` on the server. The `{ displayName, email }` "ignored" unit test is deleted rather than rewritten, replaced by a type-level `@ts-expect-error` assertion; a test that enumerates evasion shapes is strictly weaker than a signature that admits none. **This got cheaper because of the release-train decision:** with MV-157 and MV-158 in one PR there is no backward-compatibility obligation, so the signature is simply right in MV-157's first commit and there is no widening step at all.
- 2026-08-02 — **Integrator: MV-157 and MV-158 ship as ONE pull request (§J), and the "either card may merge first" language is deleted from both cards.** The prior rule — merge freely, just do not let MV-157 reach production before MV-158 merges — was not executable on this repo, where `master` is production and Vercel auto-deploys from it. Merging MV-157 alone *creates* the owner-set / `case_id`-null claim window both cards exist to prevent. A feature flag and an owner fallback were both considered and rejected (a second read path on a silent-failure seam; and MV-157 §E forbids the fallback outright). One branch, separate commits, one merge is the only atomic option under auto-deploy. Gated additionally on MV-155's and MV-156's migrations being **applied and reconciled on the hosted database**, because the merge deploys a claim path that writes `case_id`.
- 2026-08-02 — **Personal-case resolution runs before the bind, and its failure is `error`, not `expired`.** Ordering it first is what keeps the failure honestly retryable: nothing has been written to the student's row, so "try again" is true. The reverse order would produce a bound-but-case-less row, which is the one state this card exists to prevent.
- 2026-08-02 — **A leftover personal case from a failed claim is explicitly NOT an orphan.** It is a per-user singleton the account needs anyway, and creating it is idempotent. Compensating cleanup would add a delete path to the claim seam for no benefit.
- 2026-08-02 — **The demote must satisfy BOTH unique predicates while both exist.** Scoping it to `case_id` alone is the natural "case-model" rewrite and it re-creates the MV-16 dashboard-pinning regression exactly: the promote trips the surviving `(owner) where is_primary` index, the error is logged rather than thrown, and the student's dashboard silently keeps showing their first assessment. Recorded as a decision because the wrong version looks cleaner.
- 2026-08-02 — **`assessments.case_id` can never become NOT NULL** — anonymous assessments are case-less by design (MV-155) and must stay so for the MV-135 purge predicate and its partial index to keep matching. Handed to MV-160 as a named exception to "make `case_id` mandatory where the domain requires it".
- 2026-08-02 — **The MV-135 purge predicate stays keyed on `owner is null`.** The case model makes `case_id is null` look like the more natural predicate; it selects the same rows today and deletes claimed rows the moment a `case_id` write is ever lost. Two tests pin it and the swap is mutation-verified.
- 2026-08-02 — **`already-mine` heals a case-less row rather than only landing the student.** This is the runtime remedy for anything claimed in the MV-157→MV-158 window; the bulk remedy is MV-160's reconciliation sweep, which is now an explicit ordered step in **MV-160 §B** (re-run `private.mv155_backfill_personal_cases()`, then assert) rather than an assumption this card makes about a sibling. Without it, a student in that window has to re-run a claim that already "succeeded" and still sees nothing.
- 2026-08-02 — **No `requireCasePermission` call on the claim path.** The claimer is the data subject and the row has no owner until this path runs, so there is no case to authorize against yet — the conditional-update predicate is the gate, as it already is for the anonymous-recovery read (MV-28). Recorded explicitly so a reviewer running MV-151's Stage 3 checklist sees a decision rather than an omission.

- 2026-08-02 — **Integrator: assert the invariant MV-160 relies on — a claimed assessment always has a non-null `owner`.** MV-160 §B applies a CHECK to `assessments` that also covers `claimed_at`-set rows, and MV-155's repair sweep only repairs *owned* rows. If a claimed-but-`owner`-null row can exist, that `SET NOT NULL`/CHECK aborts the tighten migration against live data. The claim path is believed to always set `owner` — believed, because no card asserts it.
