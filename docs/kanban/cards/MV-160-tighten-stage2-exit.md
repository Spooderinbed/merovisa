# MV-160 — Stage 2 tighten + exit gate: case_id mandatory, compensating checks dropped, before/after data-equivalence proof

**Priority:** P1   **Owner:** agent
**Goal:** Close Stage 2 by proving its exit gate rather than declaring it — every existing student sees byte-for-byte the same data they saw before the migration (diffed against a snapshot captured *before* the first mutating migration ran, not eyeballed after), while `case_id` becomes mandatory where the domain requires it, MV-156's compensating check comes out because the composite FKs now actually bite, and no repository, constraint, index, or policy on the migrated tables still assumes the actor is the student.

## Acceptance criteria

### A — Before/after data equivalence (the headline; a proof, not an assertion)
- [ ] **A pre-migration snapshot artifact exists, captured from a copy of live production data BEFORE MV-155's first mutating migration was applied to it.** Produced by a committed script (`scripts/stage2/capture-read-path-snapshot.mjs`), run against the rehearsal copy MV-154 requires. A snapshot reconstructed after the fact, or taken from synthetic fixtures, does not satisfy this criterion and cannot be substituted.
- [ ] **The snapshot is per-user payload, not per-table counts.** For every Auth user it records the exact result of every student-facing read path: profile sections + completeness; the full assessment list and which row is primary; open and all plan items; program state / shortlist; the document list and the `document_status` checklist; the prediction → attempt → outcome timeline. Serialized deterministically (stable key order, rows sorted by id) and hashed per user × per domain, plus one whole-snapshot hash.
- [ ] **Anonymous assessments are in the snapshot too** — by id and count, with `owner is null` — so the MV-135 purge boundary is provable rather than netted away. Rows the daily purge legitimately removes during the migration window are accounted for **by id**, never absorbed into a count delta.
- [ ] **The diff is zero.** A replay script re-runs the same read paths post-migration **through MV-157's case-aware repositories**, as that user, and the produced snapshot is byte-identical to the captured one. Non-zero diff = the stage exit has failed.
- [ ] **The replay runs as the user through an RLS-scoped client** (anon key + that user's JWT), never through the service-role admin. Proving the rows survived is not the same as proving the student can still read them, and only the second one is the exit gate.
- [ ] **The normalized/excluded field list is enumerated in the script with a reason per entry, and is asserted.** At minimum `profiles.updated_at` and `user_program_state.updated_at`, which the backfill's `UPDATE` moves through `private.set_updated_at()`. Every field not on that list must match exactly. A test fails if the list grows without a reason string — a wildcard exclusion turns a byte-diff into a vibe check.
- [ ] **Row-count parity AND identity parity per table:** every pre-migration row id still exists post-migration, and the only rows Stage 2 added are the personal `cases` MV-155 minted. Nothing is destroyed.
- [ ] **A non-empty diff fails loudly and legibly** — the failure names the user, the domain, and the field that moved, so the founder can read what changed instead of being handed a hash mismatch.
- [ ] **The committed artifact is the report, not the payload.** `docs/migrations/stage2/equivalence-report.md` carries pseudonymous per-user labels, the per-domain hash pairs, counts, and the verdict. The raw snapshot JSON contains real profile sections, names and emails and **must not enter git history**: it is written to a gitignored path, the `.gitignore` entry is asserted by a test, and the file is destroyed on the rehearsal host once the report is produced.

### B — `case_id` mandatory where the domain requires it
- [ ] **The reconciliation sweep runs FIRST, as the migration's opening statement, before any `SET NOT NULL`.** Re-run `private.mv155_backfill_personal_cases()` — idempotent by construction (MV-155 §C) — as a reconciliation sweep over the residue of the MV-157 → MV-158 window and of any lost dual-write; capture its jsonb report in the migration's `raise notice`; then call `private.mv155_assert_case_backfill()`. A non-zero repair count is **recorded in the equivalence report, not swallowed** — it is the count of rows that were owned but case-less at the moment Stage 2 closed, and the founder should see it. Only then apply the NOT NULLs. Without this step the `SET NOT NULL`s below and the `assessments` CHECK abort against exactly those rows, on production, mid-migration.
- [ ] `case_id` is `NOT NULL` on the eight tables whose domain requires it: `profiles`, `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`.
- [ ] **`assessments.case_id` stays NULLABLE — the one deliberate exception**, because anonymous assessments are case-less until claimed or removed under MV-135's 3-day purge (plan step 6). It is covered instead by a CHECK expressing the real rule: an owned or claimed assessment must carry a case — `check (case_id is not null or (owner is null and claimed_at is null))`. A migration that succeeds in setting `assessments.case_id NOT NULL` has destroyed the anonymous rows; treat that as a failure, not a pass.
- [ ] Every NOT NULL is applied **after** the sweep and **before** anything in section C is dropped, in that order inside the migration.
- [ ] `documents` and `document_status` keep their legacy shape otherwise — the header/versions replacement is Stage 4 and is an explicit non-goal here. This card only makes their `case_id` mandatory.

### C — Compensating checks dropped, and the composite FKs proven live
- [ ] MV-156's compensating check **as it actually ships** — `<table>_ownership_axis_present`, `check (owner is not null or case_id is not null)` — is **dropped** on `program_predictions` / `application_attempts` / `outcome_events`, closing the nullable window the plan warned about (line 326). It is not a `check (case_id is not null)`; MV-156 deliberately ships the disjunct so the pre-MV-157 owner-only write path survives its window, and a migration written against the wrong constraint name will simply fail to find it.
- [ ] Dropping it is **safe because it becomes redundant, but only once `case_id` is NOT NULL on those three tables** — which section B applies first, in the same migration, in that order. With `case_id` NOT NULL the disjunct's right-hand branch is unconditionally true, so the check can never fire again; and the case-side FKs `(prediction_id, case_id) → program_predictions(id, case_id)` and `(attempt_id, case_id) → application_attempts(id, case_id)` can no longer be skipped by MATCH SIMPLE. An insert whose child `case_id` differs from its parent's raises **23503**. Drop it before the NOT NULL and the redundancy argument is false.
- [ ] **The counterfactual is run, not assumed:** on a scratch database, with `case_id` re-widened to nullable **and** the `_ownership_axis_present` check dropped on `application_attempts`, a null-`case_id` child inserts freely. That is the evidence that the NOT NULL — and nothing else — is what carries the enforcement once the check is gone.

### D — Legacy owner assumptions removed
- [ ] **No unique constraint, primary key, or FK target on the nine migrated tables has `owner` as a key column** — verified by querying `pg_index` / `pg_constraint`, not by reading index names. (Inherited from MV-156: `user_program_state`'s PK `(owner, program_id)` and `document_status`'s PK `(owner, kind)` must already be re-keyed onto `case_id`; this card asserts the end state and fails if either is still owner-keyed.) **Plain lookup indexes on `owner` must SURVIVE** — the criterion is deliberately not "no index has `owner` as a key column", because at least three are load-bearing after this card: `assessments_anon_purge_idx` (MV-135's 3-day purge, which MV-158 pins to the `owner is null` predicate), `assessments_owner_idx`, and whatever `owner` scan `app/api/account/delete/route.ts` still performs. Enumerate the surviving owner indexes in the PR body with the reader that needs each one; an unlisted survivor is a finding, and a deleted one is a regression.
- [ ] **The residual owner chain is dropped in this exact order, and the order is not cosmetic:** (1) the two legacy composite FKs `application_attempts foreign key (prediction_id, owner)` and `outcome_events foreign key (attempt_id, owner)` (both present in `20260620000000`); (2) *then* their `unique (id, owner)` targets on `program_predictions` / `application_attempts` / `outcome_events`; (3) *then* the now-orphaned covering index `outcome_events_attempt_id_owner_idx`. Dropping a `unique (id, owner)` while a composite FK still depends on it makes Postgres refuse the statement outright (`2BP01`) and the whole migration aborts — this is the single most likely way this card fails on first apply.
- [ ] The superseded owner-keyed **uniqueness rules** are dropped alongside them (`profiles.owner` unique, `assessments_primary_idx on (owner)`, `plan_items_kind_open_idx (owner, kind)`, `documents unique (owner, kind)`), each replaced by the case-keyed rule MV-155 §E introduced and MV-157 writes against.
- [ ] **No RLS policy predicate on the migrated tables reads `owner`.** MV-159 owns those policies; MV-160 asserts none regressed to an owner comparison — the case helpers are the only authorization source.
- [ ] **The `owner` columns are NOT dropped and no row is deleted.** Explicit non-goal — see the Decision log. This is what keeps the card's rollback a pure DDL re-application.
- [ ] **A machine-enforced source sweep** — `tests/architecture/no-actor-equals-student.test.ts`, modelled on `tests/supabase/service-role-exceptions.test.ts` — scans the live first-party tree (`lib`, `app`, `components`, `scripts`) at run time and fails on any owner-keyed data access against a migrated table outside a **registered allowlist with a reason string per entry**. The registry is read against the live source, so adding a new `.eq("owner", …)` fails the test until someone registers it. Per the access matrix's correction to MV-151's fence, the check detects the **behaviour** (a query scoped by an actor's user id), not one literal call shape — a rename must not launder it.
- [ ] **No exported repository function for a migrated domain takes a user id as its scoping argument.** The scope argument is a `caseId` (or a `CaseContext`). Enforced by type, so a regression fails `npm run typecheck` rather than a review.
- [ ] **The consultancy proof — the operational form of "no longer depends on actor equals student":** an integration test drives every migrated read *and* write path for a case with `organization_id` set, `student_user_id` **NULL**, and `owner` **NULL** on every row it creates, acting as an assigned counsellor: profile upsert + read, assessment, plan items, program state, document row + `document_status`, and the full prediction → attempt → outcome chain. If any path still needs an Auth user to function, this fails.

### E — Stage 2 exit recorded
- [ ] **MV-153's `tests/integration/tenant-isolation.itest.ts`, MV-152's `case-rls.itest.ts`, and MV-159's suites all pass UNEDITED** after the tightening. Needing to change a matrix expectation means this card moved an access-control cell and contradicts `2026-08-02-stage1-canonical-access-matrix.md` — stop and reconcile rather than update the test.
- [ ] The Stage 2 exit gate is recorded on **MV-154** with links to this card's evidence (the equivalence report, the constraint end-state assertions, the sweep, and the consultancy proof).
- [ ] **MV-154's reversibility requirement is satisfied for this slice before it runs against production:** the migration is rehearsed on the copy of live data, the rollback is written down, and both are recorded on the card. Application to the hosted project is founder-gated.

## Risk notes
- **A count-only diff is the failure mode that looks like success.** Row counts, and even per-table checksums, pass a migration that backfilled the right number of `case_id`s onto the wrong students. Reassigning one student's profile, assessment or documents to another student's case is the worst outcome Stage 2 can produce, and it is invisible to every aggregate. Per-user × per-domain payload hashes are the requirement, not a refinement of it.
- **The snapshot has an ordering dependency that cannot be repaired later.** It must exist before MV-155 runs. This is the single most likely way this card becomes unsatisfiable, and the failure is silent until the last slice of the stage.
- **The excluded-field list is where the proof gets quietly hollowed out.** Two `updated_at` columns genuinely move (the backfill `UPDATE` fires `private.set_updated_at()` on `profiles` and `user_program_state`). Everything beyond those needs a written reason and a red test when the list grows. A `case_id`-shaped exclusion, or an exclusion of a whole table, is the proof deleting itself.
- **The snapshot payload is real student PII.** Profile sections, names, emails, financial and academic detail for ~7-9 real people. Committing it to git is permanent and un-deletable, and it would contradict the layered controller model in `docs/legal/2026-07-29-stage0-decision-record.md` D-A. Only the pseudonymous hash report is committed; the payload is gitignored, the ignore is asserted, and the file is destroyed on the rehearsal host.
- **Replaying as service-role would produce a green proof of the wrong statement.** This is the same trap MV-153 called its highest risk. The replay must use an RLS-scoped client; the service-role admin is confined to capture-side seeding and teardown.
- **Order inside the migration is load-bearing three separate times, and only one of the three fails loudly.** (1) Sweep first: without `private.mv155_backfill_personal_cases()` re-run at the top, the `SET NOT NULL`s abort on production against any owned-but-case-less row — this one at least fails visibly, mid-migration, having already taken ACCESS EXCLUSIVE on eight tables. (2) NOT NULL before dropping the `_ownership_axis_present` checks: drop them while any `case_id` is still nullable and the MATCH SIMPLE hole on the three-table chain silently reopens — **nothing in the schema will complain**, which is what makes this the dangerous one. (3) The two legacy composite FKs before their `unique (id, owner)` targets: reverse that and Postgres refuses the DROP outright. Write the order into the migration as a numbered comment block, because a later reader reordering "cosmetic" DDL is how (2) happens.
- **A successful `SET NOT NULL` on `assessments.case_id` is a red flag, not a green one** — it means the anonymous rows are gone. The migration must not include it, and the tighten suite asserts the column is still nullable.
- **`SET NOT NULL` takes ACCESS EXCLUSIVE and a full scan.** At current volumes (tens of rows) this is nothing, and it will not stay nothing. If it ever matters, the idiom is `CHECK (case_id IS NOT NULL) NOT VALID` → `VALIDATE CONSTRAINT` → `SET NOT NULL`, which Postgres 12+ satisfies from the validated check. **This card cannot inherit that shortcut from MV-156** — MV-156 deliberately ships the disjunctive `check (owner is not null or case_id is not null)` instead, so that its own window does not break the owner-only write path, and a disjunct does not prove `case_id IS NOT NULL` to the planner. If volume ever makes the scan matter, this card adds the flat `NOT VALID` check itself, immediately after the sweep. Noted so the pattern is not discovered under a lock.
- **This is where dropping the `owner` columns is tempting, and it must be refused here.** It is irreversible, it destroys the provenance link the equivalence proof depends on, and Stage 4's document replacement plus Stage 6's export/deletion work still read the legacy shape. See the Decision log.
- **A string-matching sweep can be beaten by a rename.** The detector must key on the behaviour — a query scoped by an actor's user id against a migrated table — not on one literal call shape. This is precisely the correction the canonical access matrix made to MV-151's service-role fence ("detect the key, not just the import"), and it applies verbatim.
- **This card mutates LIVE user data.** MV-154's rehearsal-and-rollback discipline is not ceremony here: it is the only thing standing between a bad `SET NOT NULL` and a production outage for real students. Production application is founder-gated.
- **Do not let the tightening move an access-control cell.** If a Stage 1 matrix assertion has to be edited to stay green, the card has changed authorization behaviour and contradicts the canonical matrix. Reconcile against the spec; never update the expectation.

## Decision log
- 2026-08-02 — Card carved from Stage 2 of the revised consultancy plan (integrator session).
- 2026-08-02 — **The exit gate is a diff against a captured artifact, not a regression suite that "looks fine".** Plan line 637 says existing students see the *same* data; a passing journey test proves the app still renders, not that the rows behind it are the same rows. The snapshot is the only thing that can distinguish "correct" from "plausible", and it only exists if it was captured before the first mutating migration — which is why its absence is an escalation to MV-154, not something this card can work around.
- 2026-08-02 — **Equivalence is asserted per user × per domain, never per table.** A per-table checksum or row count passes a backfill that attached the right number of `case_id`s to the wrong students — the single worst Stage 2 outcome and the one aggregates cannot see. The unit of the proof is the payload one student can read.
- 2026-08-02 — **`assessments.case_id` stays NULLABLE as a stated domain exception**, not an oversight. Anonymous assessments are case-less by design (plan step 6) and are removed by MV-135's 3-day purge; a column-level NOT NULL would either fail the migration or, worse, succeed by destroying them. The real rule — an owned or claimed assessment must carry a case — is expressed as a CHECK instead, and the tighten suite asserts the column is still nullable so a future "tidy-up" cannot quietly close it.
- 2026-08-02 — **The `owner` columns are NOT dropped, and no row is deleted. Flagged for integrator review.** "Remove legacy owner assumptions" (plan step 13) is read as removing the assumption, not the column: no query, uniqueness rule, FK target, index or policy may derive authorization or identity from `owner`, but the column survives as the provenance link to the student's Auth user. Three reasons: it is irreversible; the equivalence proof and any post-cutover reconciliation depend on it; and Stage 4's document replacement plus Stage 6's export/deletion work still read the legacy shape. **Column removal is recorded as a Stage 6 cleanup item**, after those consumers are gone. This decision is also what keeps MV-160's rollback a pure DDL re-application.
- 2026-08-02 — **Seam check: this card owns the reconciliation sweep MV-158 delegates to it.** MV-158's criterion F2 and its Decision log both name "MV-160's reconciliation sweep" as the bulk remedy for owned-but-`case_id`-null rows; no such step existed here. Rather than push the remedy back onto MV-158 (which would make it re-derive personal cases at claim time for rows it never wrote), the sweep is added as section B's opening statement — a re-run of MV-155's idempotent `private.mv155_backfill_personal_cases()` followed by its assert. The alternative, "there will be no such rows", is exactly the assumption a `SET NOT NULL` on production is the wrong place to test. Its repair count is published in the equivalence report because a non-zero count means the MV-157 dual-write leaked, and that is a finding about Stage 2, not a housekeeping detail.
- 2026-08-02 — **Seam check: the owner chain drops FK-first, and the `owner` index criterion was narrowed.** As first drafted, section D dropped the `unique (id, owner)` targets while the legacy `(prediction_id, owner)` and `(attempt_id, owner)` FKs still depended on them — Postgres refuses that, so the migration could never have applied. The drop is now explicitly ordered FKs → unique targets → orphaned covering index. Separately, "no index on the nine tables has `owner` as a key column" was too broad: it would have condemned `assessments_anon_purge_idx`, which MV-135's purge and MV-158's `owner is null` predicate both depend on. The criterion is now about unique constraints, PKs and FK targets, and the surviving plain indexes are named and asserted present.
- 2026-08-02 — **Dropping the compensating CHECK requires a counterfactual, not an argument.** The plan's own warning (line 326) is that a composite key including a nullable column is unenforced for null rows — so the claim "the FK now covers what the check covered" is exactly the kind of claim MV-153 twice found to be unbacked. It is therefore proven twice: the FK bites (23503 on a mismatched child) and, on a scratch database with `case_id` re-widened, it does not. Only the pair establishes that the NOT NULL is load-bearing.
- 2026-08-02 — **The sweep is a machine-enforced registry, not a documented convention** — the `tests/supabase/service-role-exceptions.test.ts` shape, reading the live tree at run time and comparing against a registry with a reason per entry. And it detects the behaviour rather than one call shape, applying the canonical access matrix's correction to MV-151's fence ("detect the key, not just the import") before the same weakness is re-shipped here.
- 2026-08-02 — **"No repository assumes actor equals student" is proven operationally, not only structurally.** A grep can be satisfied by a rename. The binding evidence is a consultancy case with `student_user_id` NULL and `owner` NULL on every row driving every migrated read and write path as a counsellor — the shape Stage 3 depends on, failing here rather than in Stage 3 if any path still needs an Auth user.
- 2026-08-02 — **Only the pseudonymous hash report is committed; the snapshot payload is gitignored and destroyed.** The snapshot is real personal information for real students, and git history is permanent. Putting it in the repo to make the proof reproducible would trade a privacy obligation under D-A's layered controller model for developer convenience.
