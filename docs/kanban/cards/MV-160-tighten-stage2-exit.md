### A — Before/after data equivalence: TWO proofs, because one of them cannot live in CI

**The split, decided by the integrator 2026-08-02 and load-bearing for both halves.** The equivalence proof was originally specified as a single CI integration test that loads a pre-migration snapshot from a gitignored path and **skips when it is absent**. That cannot pass this repo's gate. The snapshot is deliberately gitignored (it is real student PII) and deliberately destroyed on the rehearsal host after the report is produced, so it is absent on **every** CI run — and Stage 1's CI treats a skipped integration test as **red**, not green (the `0 skipped` / `✓ <suite>` fail-closed log guards MV-153 took three rounds to land, precisely so a silently-skipping suite cannot green the lane). A suite that skips by design would turn every CI run red for the rest of the project's life, and the only available "fix" under deadline pressure is to weaken the guard that makes every other integration suite trustworthy. So the proof is split by what each half can honestly prove:

**A1 — Synthetic equivalence: a permanent CI test that NEVER skips.**
- [ ] **`tests/integration/stage2-data-equivalence.itest.ts` runs on seeded fixtures, contains no real PII, and has no skip path.** It seeds a production-*shaped* corpus (several Auth users; a profile each; multiple assessments with one primary; an anonymous case-less assessment; open and closed plan items across kinds; program state; documents; `document_status`; a full prediction → attempt → outcome chain), **captures the snapshot itself at the top of the test** against the pre-migration schema state, applies the Stage 2 migrations, replays every read path, and diffs. Capture and replay happen in one run, so there is no external artifact and nothing to be absent.
- [ ] **It shares ONE serializer, one hash function and one exclusion list with the live-data replay** — `scripts/stage2/capture-read-path-snapshot.mjs` and its diff module are imported by both, not reimplemented. A synthetic proof running different comparison code from the real one proves that the fixtures are equal, not that the comparison is right.
- [ ] **The skip guard is inverted into a failure.** If the suite finds itself unable to seed or unable to reach the local stack it **fails**; it never returns green and never returns skipped. The CI guard for this file is a `✓ <path>` line like every other integration suite.
- [ ] **This half proves the mechanism, and the card says plainly what it does not prove:** that the *real* students' *real* rows survived. Synthetic fixtures cannot carry the shapes that actually break a migration — a `profile_snapshot` jsonb from an early rule version, an assessment with a dropped-column attnum gap behind it, a document row whose Storage object is one of the two known orphans. A1 is the regression net; **A2 is the exit gate.**

**A2 — Live-data replay: a REHEARSAL-ONLY gate, run by the integrator, recorded as Done evidence. Not a CI test.**
- [ ] **A pre-migration snapshot artifact exists, captured from a copy of live production data BEFORE MV-155's first mutating migration was applied to it.** Produced by the same committed script (`scripts/stage2/capture-read-path-snapshot.mjs`), run against the rehearsal copy MV-154 requires. A snapshot reconstructed after the fact, or taken from synthetic fixtures, does not satisfy this criterion and cannot be substituted. **A1 passing is not a substitute for A2 and must never be recorded as one.**
- [ ] **A2 is executed by the integrator on the rehearsal host, once, as a gate on the production apply — not by CI and not by the agent.** It runs through a committed npm script (`npm run stage2:equivalence -- --snapshot <path>`) so it is reproducible, but it is invoked by hand against the restored copy, and its verdict is pasted into this card's Done evidence and into `docs/migrations/stage2/equivalence-report.md`. **The founder gate on applying Stage 2 to `obfvrxixtautamflzxzq` names this run and its date.** No green A2 record, no production apply.
- [ ] **The snapshot is per-user payload, not per-table counts.** For every Auth user it records the exact result of every student-facing read path: profile sections + completeness; the full assessment list and which row is primary; open and all plan items; program state / shortlist; the document list and the `document_status` checklist; the prediction → attempt → outcome timeline. Serialized deterministically (stable key order, rows sorted by id) and hashed per user × per domain, plus one whole-snapshot hash.
- [ ] **Anonymous assessments are in the snapshot too** — by id and count, with `owner is null` — so the MV-135 purge boundary is provable rather than netted away. Rows the daily purge legitimately removes during the migration window are accounted for **by id**, never absorbed into a count delta. **Expect this count to be ZERO and say so in the report before running it.** The plan's "40 anonymous/unclaimed" figure is from 2026-07-23; a hosted capture on 2026-08-02 found 36 assessments and **0 with `owner IS NULL`** — MV-135's purge has cleared the population, which is transient by design under a 3-day TTL. - [ ] **The replay runs as the user through an RLS-scoped client** (anon key + that user's JWT), never through the service-role admin. Proving the rows survived is not the same as proving the student can still read them, and only the second one is the exit gate.

**Shared by A1 and A2 — the comparison itself**

### B — `case_id` mandatory where the domain requires it
- [ ] **The reconciliation sweep runs FIRST, as the migration's opening statement, before any `SET NOT NULL`.** Re-run `private.mv155_backfill_personal_cases()` — idempotent by construction (MV-155 §C) — as a reconciliation sweep over the residue of the MV-157 → MV-158 window and of any lost dual-write; capture its jsonb report in the migration's `raise notice`; then call `private.mv155_assert_case_backfill()`. A non-zero repair count is **recorded in the equivalence report, not swallowed** — it is the count of rows that were owned but case-less at the moment Stage 2 closed, and the founder should see it. Only then apply the NOT NULLs. Without this step the `SET NOT NULL`s below and the `assessments` CHECK abort against exactly those rows, on production, mid-migration.
- [ ] `case_id` is `NOT NULL` on the eight tables whose domain requires it: `profiles`, `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`.
- [ ] **`assessments.case_id` stays NULLABLE — the one deliberate exception**, because anonymous assessments are case-less until claimed or removed under MV-135's 3-day purge (plan step 6). It is covered instead by a CHECK expressing the real rule: an owned or claimed assessment must carry a case — `check (case_id is not null or (owner is null and claimed_at is null))`. A migration that succeeds in setting `assessments.case_id NOT NULL` has destroyed the anonymous rows; treat that as a failure, not a pass.
- [ ] Every NOT NULL is applied **after** the sweep and **before** anything in section C is dropped, in that order inside the migration.
- [ ] `documents` and `document_status` keep their legacy shape otherwise — the header/versions replacement is Stage 4 and is an explicit non-goal here. This card only makes their `case_id` mandatory.

### C — Compensating checks dropped, the composite FKs proven live, and the immutability trigger restored
- [ ] **ALL EIGHT `<table>_ownership_axis_present` checks are dropped — not three.** MV-156's compensating check **as it actually ships** is `check (owner is not null or case_id is not null)`, named `<table>_ownership_axis_present`, on all eight owner-relaxed tables: `profiles`, `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`. It is **not** a `check (case_id is not null)`; MV-156 deliberately ships the disjunct so the pre-MV-157 owner-only write path survives its window, and a migration written against the wrong constraint name will simply fail to find it. **Corrected 2026-08-02:** this criterion previously named only the three chain tables while MV-156's acceptance said "three dropped, five survive into Stage 3" and MV-156's resume notes said "all eight" — three statements, three answers, one family of constraints. The settled answer is **all eight**, because section B sets `case_id NOT NULL` on exactly those eight, which makes the disjunct's right branch unconditionally true on every one of them. A check that can never fire is not a Stage 3 safeguard; it is a constraint the next author reads as load-bearing and plans around. MV-156's acceptance criteria and MV-154's stage criterion now say the same thing.
- [ ] Dropping them is **safe because they become redundant, but only once `case_id` is NOT NULL on those eight tables** — which section B applies first, in the same migration, in that order. On the three chain tables the second half matters too: with `case_id` NOT NULL the case-side FKs `(prediction_id, case_id) → program_predictions(id, case_id)` and `(attempt_id, case_id) → application_attempts(id, case_id)` can no longer be skipped by MATCH SIMPLE, so an insert whose child `case_id` differs from its parent's raises **23503**. Drop before the NOT NULL and the redundancy argument is false — and it fails **silently**, which is why the order is written into the migration as a numbered comment.
- [ ] **The counterfactual is run, not assumed:** on a scratch database, with `case_id` re-widened to nullable **and** the `_ownership_axis_present` check dropped on `application_attempts`, a null-`case_id` child inserts freely. That is the evidence that the NOT NULL — and nothing else — is what carries the enforcement once the check is gone.
- [ ] **`private.reject_prediction_update()` is restored to its original unconditional body, HERE, and the handoff MV-155 opened is closed on this card.** MV-155 §D narrows that trigger to permit exactly one transition (`case_id` null → not-null, every other column byte-identical) so its backfill can run, and states — twice, in its criteria and its Decision log — that "MV-160 additionally restores the original body — recorded here as a hand-off, not assumed". **No card ever accepted it.** MV-158 does not touch the trigger; MV-160's criteria and migration order did not mention it. Left open, Stage 2 exits with a narrowed immutability guard on `program_predictions` — the table whose whole point is that a prediction-of-record cannot be rewritten — and the narrowing outlives the migration it was cut for. It is *self-closing* in the sense that `old.case_id is null` becomes unreachable once `case_id` is NOT NULL, but "unreachable given a constraint elsewhere" is a weaker guarantee than "the guard says no", and a Stage 3 or Stage 6 migration that ever re-widens `case_id` would silently re-arm the allowance.
- [ ] **Ordering, and it is not free choice: the restore is the LAST statement of the migration, after section B's sweep.** Section B's opening step re-runs `private.mv155_backfill_personal_cases()`, which `UPDATE`s `program_predictions.case_id` — and that update is only permitted *by the narrowed body*. Restore the unconditional body before the sweep and the migration aborts on its own reconciliation step. Restore it before the `SET NOT NULL`s and any residue row the sweep repaired is fine, but a re-run is not. Last statement, after everything.
- [ ] **Proven by test, for `service_role` too:** after the migration, a `case_id`-only null→not-null `UPDATE` on `program_predictions` — the exact shape MV-155 permitted — **raises**, as does every other update, as `authenticated` and as `service_role`. `private.reject_prediction_update()` is SECURITY INVOKER, so `service_role` does not bypass it, and that is the property `20260620000000` exists to guarantee. Asserting only the `authenticated` case would pass against a trigger that was dropped rather than restored.

## Risk notes
- **A count-only diff is the failure mode that looks like success.** Row counts, and even per-table checksums, pass a migration that backfilled the right number of `case_id`s onto the wrong students. Reassigning one student's profile, assessment or documents to another student's case is the worst outcome Stage 2 can produce, and it is invisible to every aggregate. Per-user × per-domain payload hashes are the requirement, not a refinement of it.
- **The snapshot has an ordering dependency that cannot be repaired later.** It must exist before MV-155 runs. This is the single most likely way this card becomes unsatisfiable, and the failure is silent until the last slice of the stage.
- **The excluded-field list is where the proof gets quietly hollowed out.** Two `updated_at` columns genuinely move (the backfill `UPDATE` fires `private.set_updated_at()` on `profiles` and `user_program_state`). Everything beyond those needs a written reason and a red test when the list grows. A `case_id`-shaped exclusion, or an exclusion of a whole table, is the proof deleting itself.
- **The snapshot payload is real student PII.** Profile sections, names, emails, financial and academic detail for ~7-9 real people. Committing it to git is permanent and un-deletable, and it would contradict the layered controller model in `docs/legal/2026-07-29-stage0-decision-record.md` D-A. Only the pseudonymous hash report is committed; the payload is gitignored, the ignore is asserted, and the file is destroyed on the rehearsal host.
- **Replaying as service-role would produce a green proof of the wrong statement.** This is the same trap MV-153 called its highest risk. The replay must use an RLS-scoped client; the service-role admin is confined to capture-side seeding and teardown.
- **Order inside the migration is load-bearing FIVE separate times, and only two of the five fail loudly.** (0) **The policy rewrite goes after the `SET NOT NULL`s.** Drop the transitional owner disjunct while any row can still be case-less and that row becomes invisible to its own owner — no error, no log line, just a student whose plan or shortlist is gone. It is the same class as (2) below and the same reason: the redundancy argument for removing a guard is only true once the thing that makes it redundant is in place. (1) Sweep first: without `private.mv155_backfill_personal_cases()` re-run at the top, the `SET NOT NULL`s abort on production against any owned-but-case-less row — this one at least fails visibly, mid-migration, having already taken ACCESS EXCLUSIVE on eight tables. (2) NOT NULL before dropping the eight `_ownership_axis_present` checks: drop them while any `case_id` is still nullable and the MATCH SIMPLE hole on the three-table chain silently reopens — **nothing in the schema will complain**, which is what makes this the dangerous one. (3) The two legacy composite FKs before their `unique (id, owner)` targets: reverse that and Postgres refuses the DROP outright (`2BP01`). (4) **The `reject_prediction_update()` restore goes LAST, after the sweep** — step (1) `UPDATE`s `program_predictions.case_id`, and only MV-155's narrowed body permits that update, so restoring the unconditional body earlier makes the migration abort on its own reconciliation step. This one fails loudly but confusingly: the error names the immutability trigger, not the ordering. Write the order into the migration as a numbered comment block, because a later reader reordering "cosmetic" DDL is how (2) happens.
- **A successful `SET NOT NULL` on `assessments.case_id` is a red flag, not a green one** — it means the anonymous rows are gone. The migration must not include it, and the tighten suite asserts the column is still nullable.
- **`SET NOT NULL` takes ACCESS EXCLUSIVE and a full scan.** At current volumes (tens of rows) this is nothing, and it will not stay nothing. If it ever matters, the idiom is `CHECK (case_id IS NOT NULL) NOT VALID` → `VALIDATE CONSTRAINT` → `SET NOT NULL`, which Postgres 12+ satisfies from the validated check. **This card cannot inherit that shortcut from MV-156** — MV-156 deliberately ships the disjunctive `check (owner is not null or case_id is not null)` instead, so that its own window does not break the owner-only write path, and a disjunct does not prove `case_id IS NOT NULL` to the planner. If volume ever makes the scan matter, this card adds the flat `NOT VALID` check itself, immediately after the sweep. Noted so the pattern is not discovered under a lock.
- **This is where dropping the `owner` columns is tempting, and it must be refused here.** It is irreversible, it destroys the provenance link the equivalence proof depends on, and Stage 4's document replacement plus Stage 6's export/deletion work still read the legacy shape. See the Decision log.
- **A string-matching sweep can be beaten by a rename.** The detector must key on the behaviour — a query scoped by an actor's user id against a migrated table — not on one literal call shape. This is precisely the correction the canonical access matrix made to MV-151's service-role fence ("detect the key, not just the import"), and it applies verbatim.
- **This card mutates LIVE user data.** MV-154's rehearsal-and-rollback discipline is not ceremony here: it is the only thing standing between a bad `SET NOT NULL` and a production outage for real students. Production application is founder-gated.
- **Do not let the tightening move an access-control cell.** If a Stage 1 matrix assertion has to be edited to stay green, the card has changed authorization behaviour and contradicts the canonical matrix. Reconcile against the spec; never update the expectation.
