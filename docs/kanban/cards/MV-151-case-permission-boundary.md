# MV-151 — Case-permission server boundary (getCaseContext / requireCasePermission) + service-role exception list

**Priority:** P1   **Owner:** agent
**Goal:** Every server path that touches case-scoped data can ask one server-only layer "may this actor do this to this case?" and get a fail-closed, DB-sourced answer — so the consultancy workspace has a single, testable place that expresses owner/admin/counsellor/student permission semantics as defense in depth beneath RLS, and so no new feature can quietly reach for the service-role key to skip the check.

## Acceptance criteria
- [ ] A new server-only module tree (`lib/cases/`, each file importing `server-only`) exports `getCaseContext(actorUserId, caseId)` and `requireCasePermission(actorUserId, caseId, permission)` with the exact signatures the plan names (lines 364–365). Both take a request-scoped **authenticated** Supabase client (from `createSupabaseServerClient`); neither imports `createSupabaseAdminClient`.
- [ ] `getCaseContext` resolves, from the database only, the case's `organization_id`, the actor's membership `role` and membership `status`, whether a `case_assignments` row links the actor to this case, and whether the actor is the case's linked `student_user_id`; from those it derives the actor's access scope. It returns a null/typed-miss context for an unknown case, no membership, or an actor with no relationship to the case — never a partially-trusted context.
- [ ] The role→permission decision is a **pure** function (no I/O) that `requireCasePermission` consumes, implementing this claim-level grid (scopes: **all-org** = every case in the actor's org · **assigned** = only cases with a `case_assignments` row for the actor · **linked** = only the case whose `student_user_id` is the actor · **—** = deny). Grid derives from the plan's roles section (lines 72–101) and authorization rules (lines 348–356):

  | Permission (claim) | owner | admin | counsellor | student |
  |---|---|---|---|---|
  | `case.list` | all-org | all-org | assigned | — |
  | `case.read` | all-org | all-org | assigned | linked |
  | `case.update` | all-org | all-org | assigned | linked (permitted fields only) |
  | `case.create` | all-org | all-org | — (Stage 1 default) | — |
  | `case.assign` | all-org | all-org | — | — |
  | `case.invite_student` | all-org | all-org | assigned | — |
  | `case.export` | all-org | all-org | — | — |
  | `case.archive` | all-org | all-org | — | — |
  | `case.delete` | all-org | all-org | — | — |
  | `case.notes.internal` (read/write) | all-org | all-org | assigned | — (never) |
  | `org.audit.read` | all-org | all-org | — | — |
  | `org.manage` (team / memberships) | yes | yes | — | — |
  | `org.settings` (rename / ownership) | yes | — | — | — |

- [ ] **Inactive membership = nothing.** Any membership whose `status` is not the active value denies every claim regardless of `role` (plan line 353, 355). A revoked member's `getCaseContext` returns a no-access context even for a case they were assigned to.
- [ ] **Role is DB-sourced, never asserted.** The matrix reads `role` only from `organization_memberships` / `case_assignments` rows fetched inside `getCaseContext`. A `role` planted in the JWT, `app_metadata`, `user_metadata`, a header, or any caller-supplied argument is ignored; a test pins that a forged elevated role has no effect (plan line 101, 356).
- [ ] **Fail-closed by construction.** Unknown `caseId`, unknown `permission`, missing membership, inactive membership, or any error thrown mid-lookup resolves to **deny** — there is no code path where an exception or an unrecognized input falls through to allow. `requireCasePermission` throws a typed authorization error (or returns a typed deny the callers must handle) on denial and never returns a truthy "allowed" without a matched grid cell.
- [ ] **Enforcement-boundary doctrine documented.** A module-level doc (`lib/cases/README.md` or the module header) states: the authenticated client + RLS is the load-bearing tenant-isolation layer; this layer is defense in depth; **a bug in this layer must not by itself be sufficient to cross a tenant boundary** (plan lines 336–338). It records that every Server Component, Route Handler, Server Action, and mutation that reads or writes case-scoped data MUST call `requireCasePermission` (or gate on `getCaseContext`) first, and that routing middleware is explicitly NOT the authorization boundary (plan line 366). Because Stage 1 ships no case-touching routes, this lands as a binding convention + a Stage 3 review-gate checklist item, not a runtime assertion.
- [ ] **Service-role exception list exists and is enumerated.** A single registry module (e.g. `lib/supabase/service-role-exceptions.ts`) lists every sanctioned service-role call site for tenant/case data; each entry names the site, its justification, the case-authorization check that must precede it, and the audit event it emits (plan lines 340–344; canonical examples: invitation acceptance, account linking, storage administration, deletion jobs). The registry states plainly that the 16 pre-tenancy admin-client sites are legacy owner-based paths migrated in Stage 2, and that **new consultancy/case features must not add a service-role path outside this list** (plan line 344).
- [ ] **The exception list is machine-enforced.** An ESLint rule in `eslint.config.mjs` (a `no-restricted-imports`/`no-restricted-syntax` guard) plus a unit test that enumerates importers of `createSupabaseAdminClient` fails `npm run lint` / `npm test` when any module imports the admin client without being registered in the exception module. The guard resists the obvious evasions (re-export, alias) — a test proves an aliased/re-exported admin client is still caught.
- [ ] Scope fences held: **no** RLS SQL (MV-152), **no** `*.itest.ts` real-DB harness (MV-153), **no** UI, **no** new migration beyond what MV-150 shipped. If a query needs a column MV-150 did not ship, that is a MV-150 gap to flag — not a migration added here.

## Test plan
- **Unit — the pure matrix (the bulk of coverage):** exhaustively over every (role × permission) cell including the deny cells; inactive-membership-denies-all; unknown role → deny; unknown permission → deny; counsellor on an unassigned case → deny; counsellor on an assigned case → allow read/update/notes; student on their linked case → allow read + permitted update; student on any other case → deny; student on `case.notes.internal` → deny (never); `org.settings` owner-only vs admin. Mutation check in the spirit of MV-135: removing the `status === active` guard must fail a test.
- **Behavioral — `getCaseContext` against a fake in-memory Supabase client** (fixtures for `organizations`, `organization_memberships`, `case_assignments`, `cases`; mock `server-only` as elsewhere): resolves org/role/status/assigned/linked correctly; unknown caseId → typed miss; inactive membership → no-access context; a case in another org → no-access context; an error from the client → deny, not throw-through.
- **Behavioral — `requireCasePermission`:** allowed claims pass; denied claims raise the typed authorization error; a forged elevated `role` in caller-supplied args / mocked `user_metadata` is ignored (uses only the DB-fetched membership).
- **Guard test — the exception list:** a fixture module that imports `createSupabaseAdminClient` while absent from the registry fails the check; a registered site passes; an aliased/re-exported import is still flagged.
- **Explicitly deferred:** proof that RLS, evaluated as the authenticated user, actually denies cross-tenant reads at the database — and the full negative catalogue — is **MV-153's** real-Supabase harness and the Stage 1 exit gate, not this card. MV-151's mocked-client tests prove the layer's semantics; they do not and must not stand in for the load-bearing RLS proof.

## Risk notes
- **The biggest risk is believing this layer is the tenant boundary.** It is not — RLS as the authenticated user is (plan lines 336–338). A reviewer or a later agent may be tempted to route reads through the service-role client "because the lib already checked." That inverts the doctrine back to today's broken default. The lib must use the authenticated client so that even a matrix bug cannot cross a tenant; the SQL proof lives in MV-152 and is verified in MV-153.
- **Service-role leakage is the named Stage-1 risk** (plan risk table, "Service-role bypass"). The lint/test guard is the mitigation; it must survive alias and re-export evasion, or it is theatre. 16 admin-client importers exist today — the guard must distinguish registered legacy sites from a new unregistered case-touching path.
- **Role forgery** (plan lines 101, 356): if any code path lets `role` arrive from the session token, `user_metadata`, or a caller argument, the matrix is bypassable from the browser. DB-sourced role is non-negotiable and pinned by a test.
- **Fail-open through exceptions:** a thrown error inside a lookup that is caught and treated as "no restriction found → allow" is the classic authz defect. Every catch resolves to deny.
- **`getCaseContext` as an accidental service-role path:** if it is ever called with the admin client "to make the seed tests pass," it stops being defense-in-depth and becomes a bypass. Tests use a fake authenticated-shaped client, never the admin client.
- **Caching personalized context** (plan lines 384–391): if any per-request memoization of `getCaseContext` is introduced, its key must include both `actorUserId` and `caseId`; a key omitting either is a defect. Prefer no cross-request caching in this layer.
- **Schema-shape drift with MV-150:** `status` active-value and `role` enum spelling are defined by MV-150. Hard-coding a guessed value ("active") that MV-150 spelled differently silently denies or admits everyone. Read the merged migration; do not assume.
