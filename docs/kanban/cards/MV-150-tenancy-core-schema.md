## Acceptance criteria
- [ ] **One additive migration** under `supabase/migrations/` creates exactly six tables in `public`: `organizations`, `organization_memberships`, `cases`, `case_assignments`, `invitations`, `audit_events`. `git diff` shows **no `ALTER` to any existing table**, no owner-column change, no new trigger on any existing table, and no row written (inert on apply — mirrors the outcome-validation migration).
- [ ] **`organizations`**: `id uuid pk default gen_random_uuid()`, `name text not null`, `slug text not null` **unique**, `status text not null default 'active' check (status in ('active','suspended'))`, `created_by uuid references auth.users(id) on delete set null`, `created_at`+`updated_at timestamptz not null default now()` with a `private.set_updated_at` trigger.
- [ ] **`organization_memberships`**: `id uuid pk`, `organization_id uuid not null references organizations(id) on delete cascade`, `user_id uuid not null references auth.users(id) on delete cascade`, `role text not null check (role in ('owner','admin','counsellor'))` (student is **not** an org role — students attach via `cases.student_user_id`), `status text not null default 'active' check (status in ('active','inactive'))` (`inactive` = revoked → immediate loss, the predicate MV-152 reads), timestamps; **unique (organization_id, user_id)**.
- [ ] **`cases`**: `id uuid pk`, `organization_id uuid references organizations(id) on delete cascade` (**nullable** = personal case), `student_user_id uuid references auth.users(id) on delete set null` (**nullable** until claimed; SET NULL so deleting the student's Auth account never deletes the consultancy case), `display_name text not null`, `email text`, `operational_status text not null default 'new' check (operational_status in ('new','in_progress','waiting_on_student','ready_for_review','closed'))` (the five pilot statuses), `created_by uuid references auth.users(id) on delete set null`, `archived_at timestamptz`, timestamps.
- [ ] **`case_assignments`**: `id uuid pk`, `case_id uuid not null references cases(id) on delete cascade`, `user_id uuid not null references auth.users(id) on delete cascade`, `assignment_role text not null check (assignment_role in ('primary_counsellor'))` (extensible; pilot ships one value), timestamps; **unique (case_id, user_id)** and a **partial unique index on (case_id) where assignment_role='primary_counsellor'** (one primary per case, mirroring `assessments_primary_idx`).
- [ ] **`invitations`** (revision's single-acceptance shape): `id uuid pk`, `organization_id uuid references organizations(id) on delete cascade`, `case_id uuid references cases(id) on delete cascade` (set for a student invite), `email text not null`, `role text not null check (role in ('owner','admin','counsellor','student'))`, **`token_hash text not null unique`** (hash only — the raw token is never stored), `expires_at timestamptz not null`, `accepted_at timestamptz`, `revoked_at timestamptz`, `invited_by uuid references auth.users(id) on delete set null`, timestamps; a **shape CHECK** enforcing team-invite (`organization_id not null and case_id is null and role <> 'student'`) XOR student-invite (`case_id not null and role = 'student'`). The atomic CAS that consumes the token (`set accepted_at where token_hash=? and accepted_at is null and revoked_at is null and expires_at>now()`) is **downstream app code** (Stage 5); MV-150 ships only the columns + `unique(token_hash)` that make it enforceable at the DB level.
- [ ] **`audit_events`** (append-only): `id uuid pk`, `organization_id uuid`, `case_id uuid`, `actor_user_id uuid` — **bare uuid, deliberately no FK** (see Risk notes: the row is a tombstone that must survive org/case/user deletion and must not collide with the immutability trigger), `action text not null`, `entity_type text`, `entity_id text`, `metadata jsonb not null default '{}'` (safe metadata only — no passport numbers, no raw student detail, per plan), `created_at timestamptz not null default now()`. **No `updated_at`** (immutable).
- [ ] **Deny-all default on all six tables**: `enable row level security` **and** `force row level security`; explicit **named deny-all policies** (`using (false)` / `with check (false)`) so the locked state is greppable and intentional (not the `leads` implicit-absence style); `revoke all … from anon, authenticated` (no client grants in Stage 1). A cold **authenticated** client and an **anon** client each read zero rows and cannot INSERT/UPDATE/DELETE any of the six. Granting the reviewed privileges + real policies is **MV-152**.
- [ ] **Append-only enforced as a DB property**: `private.reject_audit_event_update()` `BEFORE UPDATE` trigger raises for **every role incl. service_role** (grants alone are insufficient — service_role bypasses RLS; mirror `private.reject_prediction_update`); no client role holds UPDATE/DELETE on `audit_events`; a single `private.write_audit_event(...)` **SECURITY DEFINER** insert choke point exists (search_path pinned; EXECUTE grants deferred to MV-152's grant review, so it is inert in Stage 1). DELETE is left to a future service-role retention/tombstone path (Stage 6), matching how `program_predictions` leaves DELETE open.
- [ ] **Indexing — advisor-clean + predicate-ready**: every FK column has a covering index; every column the Stage-1 RLS helpers will read is indexed — `organization_memberships(user_id)`, `(organization_id)`, and `status` availability; `case_assignments(case_id)`, `(user_id)`; `cases(organization_id)`, `(student_user_id)`, `(created_by)`; `audit_events(organization_id)`, `(case_id)`, `(actor_user_id)`, `(created_at)`; `invitations(organization_id)`, `(case_id)`, `(invited_by)`, `(email)`. MV-152 confirms plan efficiency and adds any partial/covering tuning its final helper predicates need.
- [ ] Every new trigger/writer function lives in schema `private` with `set search_path = ''` (advisor `function_search_path_mutable` clean).
- [ ] **`lib/supabase/types.ts` regenerated** from the migrated local schema; the six tables appear under `Database['public']['Tables']`; `npm run typecheck` passes.
- [ ] **Advisor-clean**: Supabase security + performance advisors return **no new findings** (documented) — by construction (indexed FKs, pinned search_paths, RLS enabled+forced).
- [ ] Migration applies cleanly on a fresh `npx supabase db reset` (`auto_expose_new_tables=true` exposes the new tables).

## Risk notes
- **Deny-all must be total.** Forced RLS + explicit deny-all policies + revoke-all-from-client must all hold on all six tables; a single missed `force` or a lingering grant turns MV-153's harness into a test of an open door. The itest asserts `relforcerowsecurity` per table rather than trusting the DDL by eye.
- **Append-only is a database property, not a convention** (plan). The immutability trigger must raise **even for service_role** — grants are insufficient because service_role bypasses RLS. Copy `private.reject_prediction_update` exactly.
- **Audit bare-uuid is a deliberate fork — flag for integrator review.** A real FK with `on delete set null` would fire a *system UPDATE* on the audit row when a parent is deleted, colliding with the `BEFORE UPDATE` immutability trigger and failing the parent delete; `on delete cascade` would erase history. Bare uuid + index resolves both and keeps the tombstone. Documented so the reviewer sees the trade, not an oversight.
- **Known Schema Obstacles are OUT of scope (all Stage 2).** MV-150 touches **no existing table**: it does **not** relax `owner` to nullable on the eight NOT-NULL tables, does **not** adjust the `program_predictions` immutability trigger for a `case_id` backfill, does **not** rebuild the predictions→attempts→outcomes composite FKs onto `unique (id, case_id)`, does **not** replace the document model with header+versions, does **not** retire the `storage.objects` per-user policies, and does **not** add `case_id` anywhere. Absorbing any of these breaks the additive guarantee and the sibling seams.
- **PII gate is runtime, not schema.** `cases.display_name` / `cases.email` will eventually hold student PII, but per decision record D-B no real student data enters until the consultancy agreement is executed — the columns are inert until Stage 3 with the legal gate passed. Do not seed real student data; use synthetic fixtures.
- **Local-reset grant quirk (MV-18).** A fresh `supabase db reset` recreates tables under the post-2026-05-30 default that revokes implicit service_role grants; `auto_expose_new_tables=true` in `config.toml` exposes the new tables so the admin client (and the itest) still write. **Regenerate types after a clean reset** so the shape matches what will exist on the project.
- **Enum-as-text.** Matches house convention (no native pg enums). A bad status value fails only at write time via the check; MV-151/MV-153 pin the allowed values in tests so a typo can't pass silently.

## Decision log
- 2026-07-30 — Card carved from Stage 1 of the revised consultancy plan (integrator session).
- 2026-07-30 — **Deny-all shipped as explicit named `using (false)` policies + revoke-all grants**, not the `leads` implicit-absence style, so the locked state is greppable and MV-153 can assert the named policy exists; MV-152 drops them when it adds real case-aware policies (clean "drop deny-all, add real" seam).
- 2026-07-30 — **`audit_events` columns are bare uuid with no FK.** A FK with `on delete set null` fires a system UPDATE that the append-only immutability trigger would reject (breaking parent deletes); `on delete cascade` would erase history. Bare uuid + index gives a tombstone that survives org/case/user deletion and never fights the trigger.
- 2026-07-30 — **Append-only enforced by a role-independent `BEFORE UPDATE` trigger** (mirrors `reject_prediction_update`), because service_role bypasses RLS and grants alone cannot stop a rewrite; DELETE is left to a future service-role retention path (Stage 6), matching the `program_predictions` precedent.
- 2026-07-30 — **Enums as `text … check`** (no native pg enums) and **`student` excluded from the membership role check** — students attach through `cases.student_user_id`, not memberships; `invitations.role` keeps `'student'` for the student-invite shape, gated by the XOR shape CHECK.

### Implementation decisions (build session, 2026-07-30)

- **No redundant single-column index where a unique constraint's leading column already covers the FK.** `organization_memberships.organization_id` is covered by `unique (organization_id, user_id)` and `case_assignments.case_id` by `unique (case_id, user_id)`; the advisor's `unindexed_foreign_keys` check is satisfied by a *prefix* match, so a duplicate would only cost write amplification. Every column the AC enumerates is indexed — verified from `pg_constraint`/`pg_index`, not by index name. `status` availability is provided by `organization_memberships_organization_id_status_idx` (`(organization_id, status)`), which answers "the active members of this org" from the index. A coverage map is written into the migration's footer comment.
- **The itest asserts index *coverage*, not index *names*.** It recomputes the advisor's unindexed-FK query and checks leading-column coverage per required column, so MV-152's tuning can rename or replace indexes without breaking the suite.
- **Deny-all policies target `anon, authenticated`** (the client roles Stage 1 refuses) rather than `public`. RLS default-deny already covers every other role, and naming the two client roles makes MV-152's replacement a like-for-like swap.
- **`lib/supabase/types.ts`: the `__InternalSupabase.PostgrestVersion: "14.5"` pin was preserved by hand** after regeneration. CLI 2.107.0's `gen types --local` omits that block (and adds a `graphql_public` schema block). Dropping the pin would change `createClient<Database>` type inference repo-wide — an unrelated side effect for a schema card, so it was restored. Nothing in app code reads it. **MV-151/152: expect the same two deltas on your regen.**
- **The itest needs a third env var, `SUPABASE_TEST_ANON_KEY`**, to sign a real user in and exercise the `authenticated` DB role (the existing itests only ever used the service-role client). MV-153 inherits this contract.
- **Catalog assertions and the `private.write_audit_event` call go through `psql` in the `supabase_db_*` container** (`docker exec`, container auto-discovered, overridable via `SUPABASE_TEST_DB_CONTAINER`). PostgREST cannot read `pg_catalog`, and `private` is deliberately not an exposed API schema — and the stage forbids new packages, so no `pg` client was added.
- **Empirically confirmed: `anon` and `authenticated` end up with ZERO grants on all six tables** even with `auto_expose_new_tables = true` — the migration's trailing `revoke all` wins over the auto-expose grant. `service_role` keeps full grants (and `bypassrls`), which is what lets the server path and the itest seed fixtures.
