# MV-159 — Case-aware RLS for the migrated student-owned tables (Stage 2 step 11)

**Priority:** P1   **Owner:** agent
**Goal:** The database — not just the server layer — enforces case scoping on the nine student-owned tables, so after Stage 2 a bug in a repository, a route, or MV-151's permission layer is still not sufficient to read or change another case's profile, assessment, plan, program state, prediction, attempt, outcome event, or document row.

## Acceptance criteria

**Scope — nine tables, named**
- [ ] Every owner-only policy on `profiles`, `assessments`, `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events` is **dropped and replaced** with a case-aware equivalent in one migration. `enable` + `force` row level security is true on all nine **after** the swap (verified from `pg_class`, not assumed — `documents` only gained `force` in a later fix migration, so it is the one most likely to lose it).
- [ ] One policy per table per command (no `multiple_permissive_policies`), named to the house convention (`<table>_<command>_<scope>`). The two quoted legacy `documents` policies (`"Users read own documents"`, `"Users delete own documents"`) are renamed in the process, and both gain the `to authenticated` clause they never had — today they apply to `PUBLIC`, which includes `anon`, and only the grant keeps anon out. That is the same latent-grant class MV-152 found on helper `EXECUTE`.

**The anti-recursion discipline, extended**
- [ ] Every case/assignment/membership lookup inside a policy runs through a `private` **SECURITY DEFINER STABLE** helper with `set search_path = ''`, EXECUTE revoked from `public` then granted to `authenticated` only. **No policy predicate on any of the nine tables contains an inline subquery against a `public` table** — asserted structurally from `pg_policy`, extending the assertion `case-rls.itest.ts` already runs over the six tenancy tables.
- [ ] The three parent re-assertions on `program_predictions` / `application_attempts` / `outcome_events` INSERT are re-expressed as **case parentage through definer helpers** (e.g. `private.assessment_case_id(uuid)`, `private.prediction_case_id(uuid)`, `private.attempt_case_id(uuid)`, mirroring `private.case_org_id`), not as `owner` equality and not as an inline `exists`. Observable: an authorized actor can insert a prediction whose row carries `case_id` and a null `owner`; nobody can attach a child row to a parent in a case they cannot access; and the check does not silently deny when the parent is visible to the actor only through a different disjunct of the parent's own SELECT policy.
- [ ] A new uncorrelated array helper (`private.actor_case_ids()` or equivalent) returns every case the actor may reach — student link, org owner/admin, and **membership-status-gated** assignment — so list predicates take MV-152's measured InitPlan shape `case_id = any ((select private.actor_case_ids())::uuid[])`. It is defined in terms of the existing `private.can_access_case` semantics so the two cannot drift.

**The transitional window (this card ships it; MV-160 removes it)**
- [ ] While `case_id` is nullable, every policy predicate is the disjunction `owner = (select auth.uid()) OR (case_id is not null AND <case predicate>)`. Observable with a deliberately case-less row: a row whose `case_id` is still null stays visible and updatable to its legacy owner **and to nobody else** — an org admin of an unrelated tenant sees nothing, and a case-scoped actor sees nothing. A pure case predicate would make every not-yet-backfilled row vanish from its real owner; that is the Stage 2 exit-gate failure, created here.
- [ ] **Anonymous assessments stay invisible.** A row with `owner is null AND case_id is null` is returned to **no** authenticated client, including the user who is about to claim it, and remains readable and writable by the service-role claim path (MV-158) and the MV-135 purge job. Paired with a service-role existence proof, because an RLS SELECT refusal and an empty table are indistinguishable.

**The matrix holds at the DB layer, evaluated as the authenticated user**
- [ ] Positive: a student reads and updates their own case's rows on all nine tables exactly as they could before Stage 2; an org owner/admin reaches every case in their org; an **assigned** counsellor reaches their assigned case's student data.
- [ ] Negative: an org-A actor (owner, admin, or counsellor) cannot select, update, or delete any of the nine tables' rows belonging to an org-B case; an **unassigned** org-A counsellor cannot reach an assigned-only case's student data; a student cannot reach another student's rows on any of the nine.
- [ ] Revocation is immediate on student data: flip `organization_memberships.status` to `inactive` and the same signed-in client's next select on that case's `plan_items` returns zero rows — no re-login, no token change. The dual-role rule survives: a revoked staff member who is also the linked student of their own case keeps that case's rows.
- [ ] No cell contradicts `docs/superpowers/specs/2026-08-02-stage1-canonical-access-matrix.md`. The migration carries a comment mapping each table to the matrix verb it implements (`case.read` → SELECT, `case.update` → UPDATE). **Any cell the matrix does not determine is a new decision and is written into a spec amendment, not invented in SQL** — that is exactly how MV-151 and MV-152 came to diverge in six places.

**No write hole, no widened surface**
- [ ] Every mutating policy carries **both** `using` and `with check`. `case_id` and `owner` are **not** in any column-level UPDATE grant on any of the nine tables, so re-pointing a row into another case is unexpressible by any client on any path (MV-152's mechanism — a `WITH CHECK` sees only NEW and structurally cannot say "this column may not change"); the `WITH CHECK` still asserts the NEW row lands in a case the actor may reach, as defence in depth if that grant ever widens.
- [ ] **The grant set is unchanged FROM THE POST-MV-155 BASELINE**, read column-granularly out of `information_schema` before and after this migration. **Capture that baseline from the migrated local stack at the start of the card rather than transcribing it here.** The table-level enumeration this criterion used to carry (`profiles` select+update · `assessments` select · `plan_items` select+update · `user_program_state` select+insert+update+delete · `documents` select+delete · `document_status` select+insert+update+delete · `program_predictions`/`application_attempts`/`outcome_events` select+insert+delete) is the **pre-MV-155** set and asserting it would fail: MV-155 §H revokes those flat `UPDATE`/`INSERT` grants on six tables and re-grants explicit column lists, and — per its corrected §H — adds `case_id` to the INSERT lists on the five insert-granted tables so MV-157's dual-write is expressible. This card adds **no verb and no column** to any grant; it changes **who a row is scoped to, not what a client holds**. Consultancy write verbs are Stage 3 and a grant change is a separate reviewed decision. `anon` holds nothing on any of the nine.
- [ ] `program_predictions` keeps its immutability: still no UPDATE policy, still no UPDATE grant, and `private.reject_prediction_update` still raises — including for `service_role`, and including for whatever narrowed form MV-155 left behind for the backfill. `outcome_events` stays append-only (no UPDATE policy, corrections remain a new row + `supersedes_event_id`).

**Proof it plans and proof it is clean**
- [ ] `EXPLAIN (ANALYZE, BUFFERS)` on the representative authenticated list query for each of the nine tables shows an Index Scan / Bitmap Index Scan on the MV-155 case indexes and the legacy owner indexes, **no Seq Scan**, and the helper as an **InitPlan** (once per statement, not once per row). Plans captured in the PR. Note MV-152's fixture lesson: it is tenant/case *count*, not row count, that makes the array-parameter plan appear — a too-small fixture turns this assertion into a false alarm.
- [ ] Advisors report zero new findings for these objects: no `rls_enabled_no_policy`, no `function_search_path_mutable` on the new helpers, no `multiple_permissive_policies`, no `unindexed_foreign_keys`, and **`auth_rls_initplan` is clean including `documents`** — whose two legacy policies use bare `auth.uid()` and are therefore a per-row evaluation this card fixes on the way past. (If the Supabase MCP is unauthenticated, run the advisor rules as catalog SQL against the migrated local stack, as MV-152 did, and record that the hosted `get_advisors` re-run is owed at apply time.)
- [ ] `lib/supabase/types.ts` is unchanged — this migration creates no table and alters no column.

**Harness extension (the Stage 1 harness proves nothing about these tables today)**
- [ ] `tests/integration/fixtures/tenancy.ts` seeds **student data** on cases in both orgs: a profile, ≥2 assessments including one primary, ≥1 anonymous case-less assessment, plan items (including one open per kind), program state, a document, a document_status row, and a full `prediction → attempt → outcome_event` chain — plus at least one deliberately **case-less** row on an owner-held table to exercise the transitional disjunct.
- [ ] `tests/integration/tenant-isolation.itest.ts` covers all nine tables in the cross-org denial catalogue and the positive matrix, in both directions, each denial paired with a service-role existence proof.
- [ ] `readGrantedWriteSurface()`'s completeness guard is extended to the nine tables, so a grant added to any of them without a matching probe **fails a test** — the mechanism MV-153 round 3 had to make real after claiming it for two rounds.
- [ ] **Mutation evidence, not just green.** Each new policy is reverted directly on the live local database and the suite re-run; each revert turns a *named* test red and nothing else. A passing RLS suite is worth nothing on its own — an RLS SELECT denial is silent, so `expect(data).toEqual([])` passes just as happily against a deleted policy.
- [ ] CI still proves the suite ran: if this card adds a **new** `*.itest.ts` file rather than extending the two existing ones, `.github/workflows/ci.yml` gains a `✓ <path>` guard for it. Without that, a new suite that skips every assertion greens the lane — the exact failure MV-153's round-2 MAJOR 3 found on the guards that were already there.

**Reversibility (MV-154's requirement, in the form this card takes)**
- [ ] This card mutates **no data**, so it needs no data-migration rehearsal — but it changes what live users can *see*, which is the same blast radius. Rehearsed on a copy of live data: for each of the 7 real profile owners, the set of row ids visible **as that authenticated user** on each of the nine tables is byte-identical before and after the migration. A `0 rows` result for a real student is the failure this rehearsal exists to catch, and it is silent in production.
- [ ] A stated rollback: the previous policy set, re-applied as a single reverse migration held in the PR (policy-only, so revert is exact and instant). Named in the PR body before merge, not written after an incident.

## Test plan
- **Two files, one seam, mirroring Stage 1.** `case-rls.itest.ts` owns the *policy smoke* for the nine tables — catalog shape from `pg_policy` (one policy per table per command; `polqual` **and** `polwithcheck` present on every UPDATE; no predicate naming a `public` table), the `information_schema` grant pin — **column-granular, and pinned against a baseline captured from the migrated stack at the start of this card, never against a list transcribed onto the dossier**; the post-MV-155 set is explicit column lists, not the pre-MV-155 table-level verbs, and a test that hard-codes the old enumeration fails on a correct migration — helper properties (`prosecdef`, `provolatile = 's'`, `proconfig` contains `search_path=`, owner holds `BYPASSRLS`, `anon` holds no EXECUTE), and the EXPLAIN assertions. `tenant-isolation.itest.ts` owns the *matrix* — every actor × table × verb cell. Do not duplicate across the two; MV-153's decision log records that seam and the CI guards assume it.
- **Every tenant query goes through an authenticated client.** The service-role admin is used only to seed, to tear down, and to prove that a denied read was *denied* rather than empty. A green service-role test proves exactly nothing here: `service_role` holds `BYPASSRLS`.
- **Named proofs, each its own test:**
  - *anti-recursion, structurally* — extend the `pg_policy` sweep to the nine tables; a single inline `exists` against `public.assessments` in a predicate fails it.
  - *transitional disjunct* — a case-less row is visible to its owner, invisible to a cross-tenant admin, invisible to a case-scoped actor; then backfill its `case_id` in-test and confirm the case-scoped actor gains it and the owner keeps it.
  - *anonymous assessment* — invisible to every authenticated client in the fixture (paired with a service-role existence read), still readable by the service-role claim path, still matched by the MV-135 purge predicate.
  - *parent-case re-assertion* — an actor may insert an attempt only against a prediction in a case they can reach; a consultancy-shaped row (`owner` null, `case_id` set) inserts successfully; a cross-case parent is rejected.
  - *no re-point* — `update plan_items set case_id = <other case>` and `set owner = <someone else>` are rejected `42501` (column grant), the row is verified unchanged by a service-role read, and a legitimate in-case `status` update succeeds.
  - *predictions immutability survives Stage 2* — an authenticated UPDATE is refused, and a `service_role` UPDATE still raises from the trigger.
  - *revocation immediacy on student data*, and the *dual-role* case (revoked staff who is the linked student of their own case keeps it).
  - *EXPLAIN* per table, at a fixture large enough for the planner to have a real choice.
- **Regression, not just isolation.** A test that reproduces the Stage 2 exit-gate question one card early: seed a personal case exactly as MV-155's backfill produces it, and assert the personal student's visible row set on all nine tables is identical to the pre-migration owner-scoped set. MV-160 owns the exit gate against production-shaped data; this is the cheap local version that stops MV-159 shipping the regression in the first place.
- `npm test` stays green — watch for unit suites that assert legacy policy text or owner-scoped repository behaviour; if MV-157 already moved them, this card should need no unit change at all, and needing one is a signal that a repository still assumes actor-equals-student.

## Dependencies / blocked-by
- **Hard blocker — MV-155.** `case_id` must exist on all nine tables, be backfilled from the current owner relationship, and be indexed. Without the backfill every case predicate matches nothing and the transitional owner disjunct is carrying 100% of the load — the suite would be green and the card would have proven nothing.
- **Hard blocker — MV-155's §H grant rewrite, specifically for the "grant set is unchanged" assertion.** That criterion is only meaningful relative to a baseline, and the baseline is whatever §H leaves behind: flat `UPDATE`/`INSERT` on six tables replaced by explicit column lists, with `case_id` present in the INSERT lists and absent from every UPDATE list. Write this card's grant pin **after** MV-155 is merged and applied locally, reading the real set out of `information_schema`; a pin drafted from the pre-MV-155 table-level verbs will fail, and "fixing" it by re-granting the flat verbs would silently undo §H and hand `authenticated` `UPDATE(case_id)` — the exact hole §H exists to close. If MV-155 resolved its UPSERT seam by the definer-trigger route, this card must also confirm the trigger is `security definer` with `set search_path = ''` and does not become a second, unreviewed write path.
- **Hard blocker — MV-156.** Two of its outputs are load-bearing here: (a) `owner` nullable, or a consultancy-shaped row (`owner` null, `case_id` set) cannot exist and the positive half of the parent-case re-assertion criterion is untestable; (b) the predictions→attempts→outcome_events chain re-based onto `unique (id, case_id)`, because these policies re-assert **case** parentage and the composite FK must agree with them or the two disagree row by row. Note the plan's warning (line 326): while `case_id` is nullable a composite key including it is unenforced for null rows under MATCH SIMPLE, so MV-156's compensating CHECK is what these policies lean on until MV-160.
- **Watch item MV-156 must have resolved, or this card cannot be written as specified:** `user_program_state`'s primary key is `(owner, program_id)`, `document_status`'s is `(owner, kind)`, `documents` has `unique (owner, kind)` and `profiles` has `owner uuid not null unique`. A nullable column cannot sit in a primary key. If MV-156 left those keys owner-based, say so and stop — do not invent a key swap here.
- **Coordinates with MV-157.** MV-157 moves repositories onto case authorization and dual-writes `owner` + `case_id`; these policies must admit exactly what those repositories legitimately do and nothing more. Divergence is a bug in whichever lands second — cross-check against MV-151's permission matrix and the canonical access matrix, never against the other implementation.
- **Coordinates with MV-158.** The claim path runs as `service_role` and therefore bypasses these policies, but everything the user sees *immediately after* a claim is read through the authenticated client and is governed by them. The claim itest must stay green.
- **Consumed by MV-160**, which drops the transitional owner disjunct, makes `case_id` NOT NULL where the domain requires it, and proves the stage exit.
- **Builds on MV-152's shipped helpers** (`private.can_access_case`, `can_staff_case`, `org_role`, `is_org_admin`, `case_org_id`, `actor_assigned_case_ids`, …) in `supabase/migrations/20260730180000_case_aware_rls_policies.sql`. Extend that set; do not fork it.
- A local Supabase stack (Docker) plus **a copy of live data** for the visibility rehearsal — MV-154 holds the reversibility requirement and the procedure for obtaining that copy.

## Risk notes
- **Denial is silent, and that is the defining hazard of this card.** An RLS SELECT refusal returns zero rows and no error — indistinguishable from an empty table, a fixture that never seeded, or a policy that was never created. Every "sees nothing" assertion must be paired with a service-role read proving the rows exist, and preferably with the actor who legitimately does see them. This is also the production failure mode: a wrong predicate here does not throw, it just makes a real student's assessments disappear.
- **The nullable-`case_id` window is where existing students break.** Between MV-155's backfill and MV-160's tighten, some rows will legitimately carry a null `case_id` (anonymous assessments always; anything created by a path MV-157 has not yet migrated, transiently). A pure case predicate hides them from their own owner. The owner disjunct is the mitigation, and it is only *safe* because MV-155's backfill guarantees a row's `case_id` is its owner's personal case — if that invariant is ever broken, the disjunct becomes a stale-access hole. Test the invariant, do not assume it.
- **The recursion landmine is now reachable on these tables, and it was not before.** `pp_insert_own`, `aa_insert_own` and `oe_insert_own` today contain inline `exists` subqueries against `assessments`, `program_predictions` and `application_attempts` respectively. Those peer tables are about to acquire their own policies. Two distinct failures follow: a predicate that reads a table whose policy reads back is `42P17`; and — the quieter one — **a table referenced inside a policy expression has its own RLS applied**, so a legitimate insert can be silently denied because the parent row is not visible to the actor through the disjunct the planner happened to use. Both are avoided the same way: definer helpers, never inline subqueries. Plan line 345 mandates it and MV-152 proved it structurally.
- **SECURITY DEFINER is a loaded gun, and there are now more of them.** Each new helper must pin `set search_path = ''` and fully qualify every object; derive the actor from `auth.uid()` **internally** and never trust a caller-passed user id as the authority; be STABLE and side-effect free; and have `EXECUTE` revoked from `public` *before* being granted to `authenticated` — a new function's EXECUTE defaults to PUBLIC and `anon` is in PUBLIC. MV-152 shipped that latent grant on its first green and only caught it with an assertion.
- **Widening a grant is the easiest accidental tenant hole in this card.** It is tempting, while "making these tables case-aware", to hand `authenticated` the INSERT on `assessments` or `documents` that consultancy staff will eventually need. Don't. Those verbs are Stage 3, they arrive with their own review, and the byte-identical grant assertion exists to make the temptation fail CI.
- **`program_predictions` immutability must survive being touched twice.** MV-155 adjusts the trigger to permit a `case_id`-only backfill; MV-159 then rewrites its policies. Either step can leave a general UPDATE path open. Assert the trigger still raises for `service_role` — a "no UPDATE policy" is not immutability, which is the whole reason the trigger exists.
- **Two authorization conventions will coexist in the documents bucket, deliberately.** `storage.objects` still carries the one-folder-per-user policies (plan line 328); this card scopes the `documents` *rows* to cases and leaves the objects alone, because retiring those policies is Stage 4's job alongside the header/versions replacement. Record the window rather than closing it quietly — an object path that says "user" beside a row that says "case" is exactly the kind of drift that later reads as a bug in whichever layer is examined second.
- **Performance: `actor_case_ids()` grows with a counsellor's caseload.** For the personal-student path it is a one-element array and the plan is trivial. For a busy consultancy admin it is every case in the org. Measure at a realistic case count, and remember MV-152's finding that Postgres cannot see inside `= ANY ($initplan)` and assumes ~10 elements — the plan flips on estimated selectivity, so a fixture that is too small measures the wrong plan and a fixture that is too large hides a genuine regression.
- **Scope creep with a security shape.** The student-visible-vs-consultancy-only note classification is Stage 5, not table RLS; the document header/versions model is Stage 4; audit events on sensitive reads are Stage 6. This card gates access to *rows* on nine existing tables. Anything else that arrives dressed as "while we're in here" belongs on another card.

## Decision log
- 2026-08-02 — Card carved from Stage 2 of the revised consultancy plan (integrator session).
- 2026-08-02 — Scope fixed at **nine tables** — `profiles`, `assessments`, `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events` — matching the plan's "Moving existing data to cases" domain list as it exists in the real schema. `leads` is deliberately excluded: it is RLS-on/no-policy/no-grant by design (the `harden_advisors` precedent) and carries no case.
- 2026-08-02 — **The transitional owner disjunct is this card's, and removing it is MV-160's.** Shipping a pure case predicate while `case_id` is nullable would hide not-yet-backfilled rows from their own owners — the precise regression Stage 2's exit gate forbids. The disjunct is a stated, dated, single-card-lifetime widening, not a permanent shape.
- 2026-08-02 — **The three parent re-assertions become case parentage through definer helpers, not inline `exists`.** The legacy `pp/aa/oe` INSERT policies re-assert `owner` equality via subqueries against peer tables; under the case model those subqueries are both an anti-recursion violation and a silent-denial hazard (a referenced table's own RLS applies inside a policy expression), and the owner equality is the actor-equals-student assumption Stage 2 exists to delete.
- 2026-08-02 — **The grant set does not change.** This card re-scopes rows; it does not hand `authenticated` a verb it did not already hold. Consultancy write surfaces are Stage 3 and arrive with their own review. Asserted column-granularly from `information_schema` so the rule cannot erode.
- 2026-08-02 — **Seam check: "unchanged" means unchanged from the POST-MV-155 baseline, and the baseline is measured, not transcribed.** The first draft spelled the expected grants out on the card as table-level verbs. That is the pre-MV-155 set: MV-155 §H narrows six of them to explicit column lists and puts `case_id` into the INSERT lists so MV-157's dual-write is expressible at all. A dossier-transcribed pin would have gone red on a correct migration and invited the worst available fix — re-granting the flat verbs. The pin is therefore captured from the migrated stack at the start of the card and diffed across this migration only.
- 2026-08-02 — **Re-pointing is prevented by column-level grants, with `WITH CHECK` as defence in depth**, adopting MV-152's build-time finding verbatim: a `WITH CHECK` sees only the NEW row and structurally cannot express "this column may not change", so `case_id` and `owner` stay out of the UPDATE grant entirely.
- 2026-08-02 — **`documents`' two legacy policies are fixed on the way past**: they carry no `to` clause (so they apply to `PUBLIC`, including `anon`) and use bare `auth.uid()` (a per-row `auth_rls_initplan` evaluation). Both are corrected as part of the replacement rather than filed as a separate cleanup — they are policies this card is already dropping.
- 2026-08-02 — **The harness must be extended, not assumed.** MV-153's 429 assertions cover the six tenancy tables and say nothing about `profiles`, `assessments` or `plan_items`. Extending the existing two suites (matrix in `tenant-isolation.itest.ts`, smoke in `case-rls.itest.ts`) preserves the Stage 1 seam and the CI `✓` guards; a new file would need its own guard or it can skip silently and green the lane.
- 2026-08-02 — **Reversibility takes a different form here than on MV-155/MV-156.** No data is mutated, so there is no backfill to rehearse — but visibility changes for 7 real owners, and a wrong predicate fails silently. The rehearsal is therefore a before/after visible-row-id diff per owner per table on a copy of live data, and the rollback is the previous policy set held as a reverse migration in the PR.
- 2026-08-02 — **The canonical access matrix governs; cells it does not determine are escalated, not invented.** MV-151 and MV-152 diverged in six places precisely because each derived a matrix from the plan's prose independently. Any Stage 2 cell the matrix does not cover gets a spec amendment before it gets SQL.
