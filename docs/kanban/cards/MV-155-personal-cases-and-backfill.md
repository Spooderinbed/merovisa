# MV-155 — Stage 2 personal cases + `case_id` columns + owner→case backfill across nine student-owned tables

**Priority:** P1   **Owner:** agent
**Goal:** Give every existing MeroVisa data owner a personal `case` and put a nullable, backfilled `case_id` on all nine student-owned tables — so Stage 2's repositories (MV-157), claim path (MV-158) and RLS (MV-159) have a case to scope to, while every existing student keeps seeing exactly the data they see today.

## Acceptance criteria

**A. Personal cases — created at migration, one per Auth user**
- [ ] One `case` row exists for **every row in `auth.users`** after the migration: `organization_id = null`, `student_user_id = u.id`, `created_by = u.id`, `email = u.email`, `operational_status` left at its `'new'` default. `display_name` is `coalesce(nullif(btrim(p.sections->'personal'->>'name'),''), nullif(btrim(u.raw_user_meta_data->>'full_name'),''), nullif(btrim(u.raw_user_meta_data->>'name'),''), u.email, 'MeroVisa student')` — never null, never empty (the column is `not null`).
- [ ] The population is **`auth.users`, a strict superset of the nine tables' distinct owners** (9 users vs 7 profiles at last count), so the backfill join can never miss an owner and no data-owner scan is required.
- [ ] **One personal case per user is structural:** a new partial unique index `cases_personal_student_idx on public.cases (student_user_id) where organization_id is null`. Consultancy cases (org-id non-null) are unaffected, and multiple *unlinked* personal cases remain impossible-by-absence rather than allowed.
- [ ] Creation is **idempotent** — `where not exists (…)` plus the index above; a second run inserts zero rows and raises nothing.
- [ ] **No first-use path is built here.** Users created *after* this migration have no personal case; create-or-resolve at signup/claim is MV-157/MV-158. This card states the gap; it does not fill it.

**B. `case_id` on exactly nine tables, nullable, FK to `cases`**
- [ ] `alter table … add column case_id uuid references public.cases(id) on delete restrict` on all nine: **`profiles`, `assessments`, `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`**. Nullable on every one (mandatory-where-the-domain-requires-it is MV-160).
- [ ] `on delete restrict` is deliberate and stated in the migration: while `owner` is still authoritative, `cascade` would let a case delete erase a real student's data and `set null` would orphan it silently. Case-deletion ordering is Stage 6's.
- [ ] **Nothing else gets a column.** `leads` (keyed `assessment_id` + email, no owner), `universities`, `programs`, and the six Stage-1 tenancy tables are untouched. `git diff` shows no change to any RLS **policy** on the nine tables.

**C. Backfill — one owner→case statement per table, executed through a testable function**
- [ ] The backfill lives in `private.mv155_backfill_personal_cases()` (`security definer`, `set search_path = ''`), called once by the migration and callable again by the itest and by the rehearsal. It returns a `jsonb` report — `{cases_created, profiles, assessments, plan_items, user_program_state, documents, document_status, program_predictions, application_attempts, outcome_events}` — which the migration emits via `raise notice`.
- [ ] **`revoke all on function private.mv155_backfill_personal_cases() from public;` is in the same migration, immediately after the `create`, and no role is granted `EXECUTE` in its place.** A new function's `EXECUTE` defaults to `PUBLIC`, and `authenticated` already holds `USAGE` on schema `private` (granted by `20260730180000`) — so without the revoke, any signed-in user can call, from the browser through PostgREST's RPC surface, a `security definer` function that **rewrites `case_id` on all nine student-owned tables and inserts rows into `cases`**. It is not exploitable *today* only because the function is idempotent and derives everything from `owner`; that is a property of this implementation, not a boundary. Stage 1 revoked `PUBLIC` `EXECUTE` on **every** `private` definer helper (`20260730180000_case_aware_rls_policies.sql`, the `revoke … from public` block around lines 710-741) and the discipline holds on all twelve of them today. Breaking it on the highest-blast-radius function in the schema is not a place to make the exception. This function needs **no** grantee: the migration calls it as the table owner, the itest and the rehearsal call it through `psql` as `postgres`.
- [ ] Every table's backfill has this exact shape (predictions included — see D):
      `update public.<t> t set case_id = c.id from public.cases c where c.organization_id is null and c.student_user_id = t.owner and t.owner is not null and t.case_id is null;`
- [ ] **Idempotent:** a second call updates 0 rows in every table and creates 0 cases (the `t.case_id is null` guard), proven by the itest.
- [ ] **Row-count parity:** the backfill only ever UPDATEs. No student-owned row is inserted or deleted by this migration; per-table `count(*)` is byte-identical before and after (recorded in the rehearsal log).

**D. The `program_predictions` immutability trigger — named approach, rehearsed**
- [ ] `private.reject_prediction_update()` is replaced (`create or replace`, **`set search_path = ''` restated** — MV-150's advisor discipline) with a body that permits **exactly one** transition and raises on everything else:
      `if old.case_id is null and new.case_id is not null and (to_jsonb(new) - 'case_id') = (to_jsonb(old) - 'case_id') then return new; end if; raise exception …`
- [ ] The allowance is **self-closing**: once MV-160 sets `case_id NOT NULL`, `old.case_id is null` is unreachable and the guard is unconditional again by construction. MV-160 additionally restores the original body — recorded here as a hand-off, not assumed.
- [ ] The `jsonb` comparison covers **future columns automatically** (a column added later is inside `to_jsonb`), so the allowance cannot silently widen.
- [ ] Proven by test, not by reading: a `case_id`-only null→not-null update succeeds; a `case_id` **change** (not-null→other) raises; a `case_id` update that *also* touches any other column raises; an update to `verdict`/`score_snapshot`/`rule_version` alone raises; **all four hold for `service_role` too** (the trigger is role-independent — this is the property `20260620000000` exists to guarantee).
- [ ] The approach is **rehearsed against a restored copy of live data** before it runs anywhere near production (see G).

**E. Indexes and the mirrored per-case uniqueness rules**
- [ ] Lookup indexes: `(case_id)` on `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`; `(case_id) where case_id is not null` on `assessments` (mirroring `assessments_owner_idx`'s partial idiom, so the anonymous rows never enter it) — **this one stays partial and that is not an inconsistency with the uniques below: it is a plain lookup index, never an `ON CONFLICT` arbiter, so the 42P10 inference problem does not reach it.** `profiles` is covered by its unique index below. `cases (student_user_id)` already exists from MV-150 and covers the backfill join.
- [ ] Per-case uniqueness, added **beside** the existing per-owner rules. **No `case_id is not null` predicate is applied to any of them — every case-keyed unique below is a FULL unique index. Corrected by the integrator 2026-08-02; see the Decision log.** The nullable window is still legal without it: **NULLs are distinct in a unique index**, so the legacy `case_id`-null rows do not collide with each other or with anything else. What the predicate *would* have cost is the whole of MV-157 §F: Postgres infers a **partial** unique index for `ON CONFLICT` only when the statement itself supplies the index predicate, and PostgREST's `on_conflict=` emits a **bare column list** — so every one of MV-157's upserts against a partial target raises **42P10**. A full unique on the same nullable columns *is* inferrable from a bare column list. Both halves were confirmed empirically against this project's own Postgres in a rolled-back transaction.
      - `profiles` — `unique (case_id)` *(profile per case)* — an `onConflict` arbiter (`upsertProfile`), so it **must** be full
      - `assessments` — `unique (case_id) where is_primary` *(primary assessment per case; mirrors `assessments_primary_idx`)* — **stays partial, and only on `is_primary`**: that predicate is the domain rule (non-primary rows are deliberately unconstrained), not the nullable window, and nothing upserts against it
      - `plan_items` — `unique (case_id, kind) where status = 'todo'` *(open plan item per case/kind)* — **stays partial, and only on `status = 'todo'`**, same reasoning; plus lookup `(case_id, created_at desc) where status = 'todo'` mirroring `plan_items_open_idx`
      - `user_program_state` — `unique (case_id, program_id)` *(program state per case/program)* — an `onConflict` arbiter (`upsertProgramState`), so it **must** be full
      - `documents` — `unique (case_id, kind)` — an `onConflict` arbiter (`upsertDocument`), so it **must** be full
      - `document_status` — `unique (case_id, kind)` — an `onConflict` arbiter (`setObtained`), so it **must** be full
      - `program_predictions` — `unique (case_id, assessment_id, program_id, rule_version)` — full for consistency; predictions are insert-only and nothing upserts against it
- [ ] **The four arbiter indexes are named as such in the migration comment** — `profiles (case_id)`, `user_program_state (case_id, program_id)`, `documents (case_id, kind)`, `document_status (case_id, kind)`. A later editor who adds `where case_id is not null` back to any of the four breaks MV-157 §F with a `42P10` that surfaces as a runtime error on a live upsert, not as a failed migration. The two that keep a predicate keep it for a domain reason and say so on the same line.
- [ ] **`unique (id, case_id)` composite-FK targets are NOT created here** — that swap, and the child re-pointing on `application_attempts`/`outcome_events` with its covering indexes, is MV-156.

**F. Consistency — asserted, because it cannot be a CHECK**
- [ ] `private.mv155_assert_case_backfill()` raises (aborting the migration's transaction) on any of: an owned row (`owner is not null`) with `case_id is null` on any of the nine; a row whose `case_id` resolves to a case that is not `organization_id is null and student_user_id = owner`; an assessment with `owner is null and case_id is not null`.
- [ ] **`revoke all on function private.mv155_assert_case_backfill() from public;` in the same migration, same reasoning as §C.** This one is read-only, so the exposure is a disclosure channel rather than a write channel — but the rule is "every `private` definer function has PUBLIC EXECUTE revoked", and a rule with a judgement call in it is not a rule. `EXECUTE` is granted to no role; the migration, the itest and MV-160's sweep all call it as `postgres`.
- [ ] The migration calls it as its **last statement**; the itest calls the same function after seeding, so migration and test enforce one invariant, not two descriptions of one.
- [ ] Stated in the migration comment and here: the owner↔case invariant is **cross-table**, so no `CHECK` can express it. A `NOT VALID` check is not a substitute — Postgres still enforces it on new rows, which would break every live owner-only write between this card and MV-157. Enforcement becomes structural at MV-156 (composite FKs) and MV-160 (`NOT NULL` + drop legacy).

**H. `case_id` is not client-writable**
- [ ] Adding a column to a table with a **table-level** `GRANT` silently extends that grant to the new column. On the nine tables `authenticated` currently holds table-level `UPDATE` (`profiles`, `plan_items`, `user_program_state`, `document_status`) and `INSERT` (`user_program_state`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`). Each of those grants is **replaced with an explicit column list** (MV-152's split-the-flat-grant remedy): e.g. `revoke update on public.profiles from authenticated; grant update (sections, completeness) on public.profiles to authenticated;`.
- [ ] **`case_id` is OMITTED from every UPDATE column list, and INCLUDED in every INSERT column list.** That asymmetry is the whole point of the section and it is not a slip. UPDATE is where the hazard lives: a client that can `UPDATE case_id` can re-point an existing row into another case. An INSERT cannot re-point anything — it creates a row, and MV-159's `WITH CHECK` constrains which case the inserted value may name. So `case_id` appears in the INSERT lists on `user_program_state`, `document_status`, `program_predictions`, `application_attempts` and `outcome_events`, and appears in **no** UPDATE list anywhere.
- [ ] **Why the INSERT grant is not optional: three authenticated-client paths must write `case_id` under MV-157, and no other card grants it.** MV-157 §G says "do not add grants in this card"; MV-159 asserts the grant set is unchanged. If this card omits `case_id` from the INSERT lists, all three fail with `42501` the moment MV-157's dual-write lands, and the gap is closed nowhere. The three, verified against the live tree: `app/api/documents/status/route.ts` (`createSupabaseServerClient()` → `setObtained` on `document_status`), `app/api/shortlist/route.ts` (which MV-157 §G flips onto the authenticated client → `upsertProgramState` on `user_program_state`), and `captureApplication` in `lib/outcomes/on-apply.ts` (which MV-157 §G states "already runs on the RLS-scoped client" → inserts on `program_predictions`, `application_attempts`, `outcome_events`).
- [ ] **Unresolved seam, named here rather than discovered in production: the two PostgREST UPSERT paths.** `upsertProgramState` and `setObtained` are upserts, not inserts. PostgREST compiles them to `INSERT … ON CONFLICT DO UPDATE SET`, and the `SET` list covers every column in the payload — so once MV-157 puts `case_id` in the payload, those two statements need `UPDATE(case_id)` as well as `INSERT(case_id)`, which this section deliberately refuses to grant. This card does **not** leave that to MV-157 to trip over. **RESOLVED BY THE INTEGRATOR, 2026-08-02: take (a)** — rationale in the Decision log. The two candidates were: **(a)** a `before insert or update` **definer trigger** on `user_program_state` and `document_status` that derives `case_id` from `owner` server-side, so the client never supplies it and neither grant is needed (preferred — it also makes the dual-write unforgeable rather than merely permitted); or **(b)** those two paths stay on the **service-role client** until MV-159's grant review, which means MV-157 §G does not flip `app/api/shortlist/route.ts` and must say so. The answer is written down here, on the card that owns the grants, and it is **(a)**. **MV-157 §G's flip of `app/api/shortlist/route.ts` therefore stands** — do not revert it.
- [ ] **The trigger fires ONLY when `NEW.owner IS NOT NULL`, and the `WHEN` clause is part of the specification, not an optimisation:** `create trigger … before insert or update on public.<t> for each row when (new.owner is not null) execute function private.<fn>();`. Integrator decision, 2026-08-02 — the unqualified form made MV-160 §D unsatisfiable. Two branches, both acceptance criteria:
      - **`owner` set (a personal case).** The trigger derives `case_id` from that owner's personal case and **overwrites** whatever the statement supplied. The original hazard — a client re-pointing its own row into another case — stays closed, and closed at the strongest available point: not by a grant somebody could widen later, but by the row never carrying a client-chosen value at all.
      - **`owner IS NULL` (a consultancy-created row).** There is nothing to derive from, the trigger does not fire, and the **statement-supplied `case_id` is honoured**. The bound on *which* case it may name is **MV-159's `WITH CHECK`**, not this trigger. `case_id` is in the INSERT grant list on both tables precisely so this is expressible.
      - **Why the qualification is not optional.** An unqualified trigger has no owner to derive from when `owner IS NULL`, and its "overwrite what the client supplied" hardening then destroys the only value that could have identified the case. MV-160 §D's write half requires an assigned counsellor to INSERT / UPDATE / DELETE on exactly these two tables **with `owner IS NULL`**; against the unqualified form that proof is unsatisfiable by construction, and the two criteria could not both hold.
- [ ] **What the trigger buys, and the one seam it deliberately leaves open — stated here rather than found in Stage 3.** Its purpose is that on the two upsert tables the client supplies **no `case_id` at all**, so PostgREST's `ON CONFLICT DO UPDATE SET` list never names the column and `UPDATE(case_id)` is never needed. **MV-157 must therefore keep `case_id` out of the `upsertProgramState` and `setObtained` payloads**: a payload that carries it fails the grant check with `42501` *before* any trigger runs — that is the seam this option closes, not a case it handles. The consequence for the `owner IS NULL` branch follows and is accepted: a **consultancy row written through an upsert** must supply `case_id`, so it would need `UPDATE(case_id)`, which Stage 2 does not grant. **No Stage 2 caller does this** — consultancy writes arrive in Stage 3 — and MV-160 §D's write half drives plain `INSERT` / `UPDATE` / `DELETE` statements, which need only the grants that exist. Recorded as a **Stage 3 input** alongside the deferred verbs in `docs/superpowers/specs/2026-08-02-stage2-migration-and-access-matrix.md` §6.
- [ ] **The UPSERT-seam trigger function carries the same revoke.** Option (a)'s `before insert or update` function on `user_program_state` and `document_status` is `security definer` with `set search_path = ''`, and its `EXECUTE` is **revoked from `public`** in the same migration. A trigger fires as the table owner regardless of who holds `EXECUTE`, so the revoke costs nothing functionally — what it removes is the ability for any signed-in client to invoke a definer function **directly** through PostgREST RPC, outside a trigger context, with a hand-built `record`. Same rule, same three-word statement, applied to all three new definer objects: `mv155_backfill_personal_cases`, `mv155_assert_case_backfill`, and this trigger function.
- [ ] `assessments` (`select` only) and `documents` (`select, delete`) need no change — stated so a reviewer sees the omission is deliberate.
- [ ] **Behaviour-preserving:** no current code path writes `case_id`, so every existing repository call still succeeds. Proven by `npm test` staying green and by the itest exercising the real upsert/insert paths for `user_program_state` and `document_status` through an **authenticated** client.
- [ ] The itest asserts the resulting grant set on the nine tables **column-granularly out of `information_schema`** (the `readGrantedWriteSurface()` idiom from `tests/integration/fixtures/tenancy.ts`), so a later migration cannot re-open the hole silently. MV-159 must preserve it — and must be told the post-MV-155 set is the baseline, not the pre-MV-155 table-level set.

**H2. Right to delete — the contract this card would otherwise have broken**
- [ ] **A personal case must not survive its student's account deletion.** `cases.student_user_id` is `ON DELETE SET NULL` while all nine student tables are `ON DELETE CASCADE` on `owner`, so `admin.auth.admin.deleteUser(userId)` cascades every student row away and **leaves the cases row standing**, carrying `display_name` (their real name) and `email` (their real address), unlinked and therefore un-findable. `/api/account/delete`'s docstring promises it "removes every trace of the signed-in user" — true today only because `public.cases` holds zero rows, **false from the moment this migration applies**. It is a privacy regression introduced by this card, so this card closes it.
- [ ] **Closed in the route, not by a database rule, and the reason is ordering.** The case can only be deleted *after* the nine (their `case_id` FKs are `ON DELETE RESTRICT`) and *before* the Auth user (`student_user_id` is nulled by the cascade, after which the row cannot be identified as theirs). No FK action expresses that window: `ON DELETE CASCADE` on `student_user_id` would also destroy **consultancy** cases for the same student, which belong to the organisation and are Stage 3's; a `BEFORE DELETE` trigger on `auth.users` runs while the nine still reference the case (`23503`); an `AFTER DELETE` trigger depends on firing order against Postgres's internal RI triggers, which is unspecified. The route already owns this contract and its docstring is the thing that was false.
- [ ] **`OWNED_TABLES` is now all nine, children before parents.** The four that were left to the `owner` FK cascade (`document_status`, `program_predictions`, `application_attempts`, `outcome_events`) must be explicit, or the `RESTRICT` FKs block the case delete.
- [ ] **A failed case delete stops before `deleteUser`.** It is the one step that gets *worse* if the route continues: destroying the identity strips the only link to the surviving case and no retry could ever find it. Every other step degrades safely (its rows cascade away with the Auth row), so the guard is specific rather than a blanket abort.
- [ ] **`organization_id IS NULL` is in the predicate**, so a consultancy case for the same student survives — asserted, not assumed.
- [ ] **Proven by a real-DB test** that drives the actual route (not a replay of its delete sequence) against the local stack, then sweeps `public.cases` for the student's name and email **including rows whose `student_user_id` is already NULL** — the exact shape the regression produced and the shape a link-based check would miss.

## Risk notes
- **This is the first migration in the programme that mutates live user data.** Nine Auth users, 7 profiles, ~76 assessments, 74 plan items, 12 program-state rows, 6 documents, 10 predictions, 10 attempts, 19 outcome events — small enough that an in-place backfill is practical, small enough that a mistake destroys a meaningful fraction of everything the product holds. Rehearsal + rollback are not ceremony; they are the reason this card is separable from MV-156.
- **The migration is inert locally and consequential in production.** No `auth.users` exist after `db reset`, so the backfill is a no-op and the itest has to construct its own pre-migration world. A cold agent who reads "green locally" as "safe" has tested the DDL and none of the data movement.
- **`document_status` was never counted** in the plan's feasibility inspection. Its shape (`primary key (owner, kind)`) means its owner column is also a PK column — re-count it at rehearsal and do not assume it is empty.
- **`user_program_state` and `document_status` have `owner` inside their PRIMARY KEY.** Postgres forbids a nullable PK column, so **MV-156 cannot simply `alter column owner drop not null` on those two — it must replace the primary key**. Flagged here because this card's index choices must not make that harder: the new per-case uniques are separate partial indexes, not PK changes, so MV-156 is free to re-key.
- **Adding a column inherits the table-level grant.** This is the one way an additive migration can widen the client write surface, and it is why §H exists. Without it a student could `update profiles set case_id = <another case>` through the anon key the moment MV-159's policies start trusting `case_id`.
- **Narrowing the immutability trigger is a real, if bounded, widening of an invariant the codebase treats as absolute.** The alternative — drop the trigger, update, recreate, all under the `ACCESS EXCLUSIVE` lock the DDL takes — is safe against concurrent writers but leaves the *backfill statement itself* unguarded, so a mistyped `set` in the same transaction would rewrite a prediction-of-record with nothing raising. The narrowed trigger keeps the guard live during the exact operation it is protecting against. It is self-closing at MV-160 and must be restored to its unconditional body there.
- **`on delete restrict` interacts with MV-153's teardown.** The Stage-1 fixtures delete seeded cases in `afterAll`; restrict only bites if a student-owned row references them, which those fixtures never create. Verify by running the full integration suite, not by reasoning about it.
- **`cases_personal_student_idx` could collide with existing fixtures.** `tests/integration/fixtures/tenancy.ts` seeds many cases; if any run seeds two `organization_id is null` cases for one auth user, this index turns both Stage 1 suites red at the fixture, not at an assertion. Check before writing the index, and fix the fixture rather than weakening the index.
- **Account deletion left a NAME-AND-EMAIL record standing, and this card fixes it (§H2).** `owner` is `on delete cascade` (child rows vanish) while `cases.student_user_id` is `on delete set null`, so deleting an Auth user cascades every student row away and leaves the personal case behind. **The earlier wording of this note — "an empty, unlinked personal case … harmless now" — was wrong on the load-bearing word.** The row is not empty: `display_name` carries the student's real name and `email` their real address, both `not null`/populated by the backfill's own coalesce chain, and `student_user_id` NULL only makes it *un-findable*, not *harmless*. Nulling the link removes the ability to answer "whose is this?", which is the opposite of a mitigation. `/api/account/delete` promises to remove "every trace of the signed-in user", and that promise is true today only because `public.cases` is empty — this migration is what makes it false. It is therefore **not** a pre-existing retention artefact to hand to Stage 6 / MV-05: it is a privacy regression introduced here, and §H2 closes it here. What *does* remain Stage 6's is the lifecycle of **consultancy** cases when a student deletes their account, which this card deliberately leaves standing.
- **Anonymous assessments must stay case-less — and there are currently ZERO of them, which changes how this is proven, not whether.** Giving an unclaimed row a case would take it out of MV-135's `owner is null` purge predicate and turn a shipped retention promise into a lie; the reconciliation function asserts `owner is null ⇒ case_id is null` precisely so a future well-meaning backfill cannot do this. **The count is stale everywhere in this carve:** the plan's "40 anonymous/unclaimed" is from 2026-07-23; a hosted capture on 2026-08-02 found 36 assessments and **0 with `owner IS NULL`** — MV-135's purge has cleared the population, which is transient by design under a 3-day TTL. The consequence is concrete and is not "update the number": **the backfill's anonymous-stays-case-less behaviour has no production data to exercise**, so it is provable only by the synthetic seed in the itest, and the rehearsal against live data cannot confirm it. Do not read a rehearsal log showing "0 anonymous rows left case-less" as evidence that the branch works; read it as evidence the branch was never entered.
- **The documents model is NOT replaced here.** `documents` and `document_status` get a `case_id` column and nothing else — no `document_requests`/`document_versions`/`document_reviews`, no mapping of status into request/review state, no `storage.objects` policy retirement, no object re-pathing. Absorbing any of that collapses the Stage 4 seam and makes this card's rollback untestable.

## Decision log
- 2026-08-02 — Card carved from Stage 2 of the revised consultancy plan (integrator session).
