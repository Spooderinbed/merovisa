# MV-155 — Stage 2 personal cases + `case_id` columns + owner→case backfill across nine student-owned tables

**Priority:** P1   **Owner:** agent
**Goal:** Give every existing MeroVisa data owner a personal `case` and put a nullable, backfilled `case_id` on all nine student-owned tables — so Stage 2's repositories (MV-157), claim path (MV-158) and RLS (MV-159) have a case to scope to, while every existing student keeps seeing exactly the data they see today.

## Acceptance criteria

**A. Personal cases — created at migration, one per Auth user**
- [ ] One `case` row exists for **every row in `auth.users`** after the migration: `organization_id = null`, `student_user_id = u.id`, `created_by = u.id`, `email = u.email`, `operational_status` left at its `'new'` default. `display_name` is `coalesce(nullif(btrim(p.sections->'personal'->>'name'),''), nullif(btrim(u.raw_user_meta_data->>'full_name'),''), nullif(btrim(u.raw_user_meta_data->>'name'),''), u.email, 'MeroVisa student')` — never null, never empty (the column is `not null`).
- [ ] The population is **`auth.users`, a strict superset of the nine tables' distinct owners** (9 users vs 7 profiles at last count), so the backfill join can never miss an owner and no data-owner scan is required.
- [ ] **One personal case per user is structural:** a new partial unique index `cases_personal_student_idx on public.cases (student_user_id) where organization_id is null`. Consultancy cases (org-id non-null) are unaffected, and multiple *unlinked* personal cases remain impossible-by-absence rather than allowed.
- [ ] Creation is **idempotent** — `where not exists (…)` plus the index above; a second run inserts zero rows and raises nothing.
- [ ] **No first-use path is built here.** Users created *after* this migration have no personal case; create-or-resolve at signup/claim is MV-157/MV-158. This card states the gap; it does not fill it.

**B. `case_id` on exactly nine tables, nullable, FK to `cases`**
- [ ] `alter table … add column case_id uuid references public.cases(id) on delete restrict` on all nine: **`profiles`, `assessments`, `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`**. Nullable on every one (mandatory-where-the-domain-requires-it is MV-160).
- [ ] `on delete restrict` is deliberate and stated in the migration: while `owner` is still authoritative, `cascade` would let a case delete erase a real student's data and `set null` would orphan it silently. Case-deletion ordering is Stage 6's.
- [ ] **Nothing else gets a column.** `leads` (keyed `assessment_id` + email, no owner), `universities`, `programs`, and the six Stage-1 tenancy tables are untouched. `git diff` shows no change to any RLS **policy** on the nine tables.

**C. Backfill — one owner→case statement per table, executed through a testable function**
- [ ] The backfill lives in `private.mv155_backfill_personal_cases()` (`security definer`, `set search_path = ''`), called once by the migration and callable again by the itest and by the rehearsal. It returns a `jsonb` report — `{cases_created, profiles, assessments, plan_items, user_program_state, documents, document_status, program_predictions, application_attempts, outcome_events}` — which the migration emits via `raise notice`.
- [ ] **`revoke all on function private.mv155_backfill_personal_cases() from public;` is in the same migration, immediately after the `create`, and no role is granted `EXECUTE` in its place.** A new function's `EXECUTE` defaults to `PUBLIC`, and `authenticated` already holds `USAGE` on schema `private` (granted by `20260730180000`) — so without the revoke, any signed-in user can call, from the browser through PostgREST's RPC surface, a `security definer` function that **rewrites `case_id` on all nine student-owned tables and inserts rows into `cases`**. It is not exploitable *today* only because the function is idempotent and derives everything from `owner`; that is a property of this implementation, not a boundary. Stage 1 revoked `PUBLIC` `EXECUTE` on **every** `private` definer helper (`20260730180000_case_aware_rls_policies.sql`, the `revoke … from public` block around lines 710-741) and the discipline holds on all twelve of them today. Breaking it on the highest-blast-radius function in the schema is not a place to make the exception. This function needs **no** grantee: the migration calls it as the table owner, the itest and the rehearsal call it through `psql` as `postgres`.
- [ ] Every table's backfill has this exact shape (predictions included — see D):
      `update public.<t> t set case_id = c.id from public.cases c where c.organization_id is null and c.student_user_id = t.owner and t.owner is not null and t.case_id is null;`
- [ ] **Idempotent:** a second call updates 0 rows in every table and creates 0 cases (the `t.case_id is null` guard), proven by the itest.
- [ ] **Row-count parity:** the backfill only ever UPDATEs. No student-owned row is inserted or deleted by this migration; per-table `count(*)` is byte-identical before and after (recorded in the rehearsal log).

**D. The `program_predictions` immutability trigger — named approach, rehearsed**
- [ ] `private.reject_prediction_update()` is replaced (`create or replace`, **`set search_path = ''` restated** — MV-150's advisor discipline) with a body that permits **exactly one** transition and raises on everything else:
      `if old.case_id is null and new.case_id is not null and (to_jsonb(new) - 'case_id') = (to_jsonb(old) - 'case_id') then return new; end if; raise exception …`
- [ ] The allowance is **self-closing**: once MV-160 sets `case_id NOT NULL`, `old.case_id is null` is unreachable and the guard is unconditional again by construction. MV-160 additionally restores the original body — recorded here as a hand-off, not assumed.
- [ ] The `jsonb` comparison covers **future columns automatically** (a column added later is inside `to_jsonb`), so the allowance cannot silently widen.
- [ ] Proven by test, not by reading: a `case_id`-only null→not-null update succeeds; a `case_id` **change** (not-null→other) raises; a `case_id` update that *also* touches any other column raises; an update to `verdict`/`score_snapshot`/`rule_version` alone raises; **all four hold for `service_role` too** (the trigger is role-independent — this is the property `20260620000000` exists to guarantee).
- [ ] The approach is **rehearsed against a restored copy of live data** before it runs anywhere near production (see G).

**E. Indexes and the mirrored per-case uniqueness rules**
- [ ] Lookup indexes: `(case_id)` on `plan_items`, `user_program_state`, `documents`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`; `(case_id) where case_id is not null` on `assessments` (mirroring `assessments_owner_idx`'s partial idiom, so the anonymous rows never enter it). `profiles` is covered by its unique index below. `cases (student_user_id)` already exists from MV-150 and covers the backfill join.
- [ ] Per-case uniqueness, added **beside** the existing per-owner rules and partial on `case_id is not null` so the nullable window is legal:
      - `profiles` — `unique (case_id) where case_id is not null` *(profile per case)*
      - `assessments` — `unique (case_id) where is_primary and case_id is not null` *(primary assessment per case; mirrors `assessments_primary_idx`)*
      - `plan_items` — `unique (case_id, kind) where status = 'todo' and case_id is not null` *(open plan item per case/kind)*, plus `(case_id, created_at desc) where status = 'todo'` mirroring `plan_items_open_idx`
      - `user_program_state` — `unique (case_id, program_id) where case_id is not null` *(program state per case/program)*
      - `documents` — `unique (case_id, kind) where case_id is not null`
      - `document_status` — `unique (case_id, kind) where case_id is not null`
      - `program_predictions` — `unique (case_id, assessment_id, program_id, rule_version) where case_id is not null`
- [ ] **`unique (id, case_id)` composite-FK targets are NOT created here** — that swap, and the child re-pointing on `application_attempts`/`outcome_events` with its covering indexes, is MV-156.

**F. Consistency — asserted, because it cannot be a CHECK**
- [ ] `private.mv155_assert_case_backfill()` raises (aborting the migration's transaction) on any of: an owned row (`owner is not null`) with `case_id is null` on any of the nine; a row whose `case_id` resolves to a case that is not `organization_id is null and student_user_id = owner`; an assessment with `owner is null and case_id is not null`.
- [ ] **`revoke all on function private.mv155_assert_case_backfill() from public;` in the same migration, same reasoning as §C.** This one is read-only, so the exposure is a disclosure channel rather than a write channel — but the rule is "every `private` definer function has PUBLIC EXECUTE revoked", and a rule with a judgement call in it is not a rule. `EXECUTE` is granted to no role; the migration, the itest and MV-160's sweep all call it as `postgres`.
- [ ] The migration calls it as its **last statement**; the itest calls the same function after seeding, so migration and test enforce one invariant, not two descriptions of one.
- [ ] Stated in the migration comment and here: the owner↔case invariant is **cross-table**, so no `CHECK` can express it. A `NOT VALID` check is not a substitute — Postgres still enforces it on new rows, which would break every live owner-only write between this card and MV-157. Enforcement becomes structural at MV-156 (composite FKs) and MV-160 (`NOT NULL` + drop legacy).

**G. Reversibility — this is the first card that mutates live user data**
- [ ] A **rehearsal on a restored copy of live data** is done before the migration is proposed for production, and its log is the card's Done evidence: per-table counts before/after, the backfill report jsonb, personal cases created, predictions updated, anonymous assessments left case-less, wall-clock, and `mv155_assert_case_backfill()` returning clean.
- [ ] A checked-in, **rehearsed** rollback `supabase/rehearsal/MV-155-rollback.sql` (a script, not a migration), ordered — and the order changed 2026-08-02 to match `2026-08-02-stage2-migration-and-access-matrix.md` §10.1 **R6**, which is authoritative: (1) restore the original unconditional `private.reject_prediction_update()` body **FIRST**, so no instant exists in which predictions are updatable and the column is already gone; (2) `alter table … drop column case_id` ×9 — which drops the FKs and every index in E with the column; (3) `drop trigger` + `drop function` for §H's UPSERT-seam definer trigger on `user_program_state` and `document_status` — **an earlier draft of this list omitted it**, which would have left a definer trigger deriving `case_id` from `owner` on two tables that no longer have a `case_id` column; (4) restore the flat table-level `UPDATE` / `INSERT` grants on the six tables §H rewrote — also omitted from the earlier draft, and its absence leaves `authenticated` holding column lists that name a dropped column; (5) `drop function private.mv155_backfill_personal_cases()` and `private.mv155_assert_case_backfill()`; (6) `drop index public.cases_personal_student_idx`; (7) `delete from public.cases where organization_id is null and student_user_id is not null`.
- [ ] **This slice rollback is valid only against the immediate predecessor state, and it stops being runnable once MV-156 lands.** Per §10.1 of the matrix spec, MV-156's `_ownership_axis_present` checks and case-side composite FKs depend on `case_id`, so `drop column case_id` is refused (`2BP01`) after MV-156 applies, and the personal-case delete then fails on `ON DELETE RESTRICT`. The real unwind after that point is the stage-level reverse sweep R1→R6, not this script. Write that sentence into the script's header, not only here.
- [ ] The rollback's **expiry is written into the script**: step 3 is valid **only until MV-157 merges**. After MV-157 ships a live create-or-resolve path, a blanket delete of personal cases would destroy cases created by real signups, and the step must be narrowed to a recorded id list.
- [ ] The migration is **data-dependent and inert on an empty database** — a fresh `supabase db reset` has no `auth.users`, so it creates 0 cases and updates 0 rows. This is exactly why local green is not evidence and the rehearsal is mandatory.

**H. `case_id` is not client-writable**
- [ ] Adding a column to a table with a **table-level** `GRANT` silently extends that grant to the new column. On the nine tables `authenticated` currently holds table-level `UPDATE` (`profiles`, `plan_items`, `user_program_state`, `document_status`) and `INSERT` (`user_program_state`, `document_status`, `program_predictions`, `application_attempts`, `outcome_events`). Each of those grants is **replaced with an explicit column list** (MV-152's split-the-flat-grant remedy): e.g. `revoke update on public.profiles from authenticated; grant update (sections, completeness) on public.profiles to authenticated;`.
- [ ] **`case_id` is OMITTED from every UPDATE column list, and INCLUDED in every INSERT column list.** That asymmetry is the whole point of the section and it is not a slip. UPDATE is where the hazard lives: a client that can `UPDATE case_id` can re-point an existing row into another case. An INSERT cannot re-point anything — it creates a row, and MV-159's `WITH CHECK` constrains which case the inserted value may name. So `case_id` appears in the INSERT lists on `user_program_state`, `document_status`, `program_predictions`, `application_attempts` and `outcome_events`, and appears in **no** UPDATE list anywhere.
- [ ] **Why the INSERT grant is not optional: three authenticated-client paths must write `case_id` under MV-157, and no other card grants it.** MV-157 §G says "do not add grants in this card"; MV-159 asserts the grant set is unchanged. If this card omits `case_id` from the INSERT lists, all three fail with `42501` the moment MV-157's dual-write lands, and the gap is closed nowhere. The three, verified against the live tree: `app/api/documents/status/route.ts` (`createSupabaseServerClient()` → `setObtained` on `document_status`), `app/api/shortlist/route.ts` (which MV-157 §G flips onto the authenticated client → `upsertProgramState` on `user_program_state`), and `captureApplication` in `lib/outcomes/on-apply.ts` (which MV-157 §G states "already runs on the RLS-scoped client" → inserts on `program_predictions`, `application_attempts`, `outcome_events`).
- [ ] **Unresolved seam, named here rather than discovered in production: the two PostgREST UPSERT paths.** `upsertProgramState` and `setObtained` are upserts, not inserts. PostgREST compiles them to `INSERT … ON CONFLICT DO UPDATE SET`, and the `SET` list covers every column in the payload — so once MV-157 puts `case_id` in the payload, those two statements need `UPDATE(case_id)` as well as `INSERT(case_id)`, which this section deliberately refuses to grant. This card does **not** leave that to MV-157 to trip over. **RESOLVED BY THE INTEGRATOR, 2026-08-02: take (a)** — rationale in the Decision log. The two candidates were: **(a)** a `before insert or update` **definer trigger** on `user_program_state` and `document_status` that derives `case_id` from `owner` server-side, so the client never supplies it and neither grant is needed (preferred — it also makes the dual-write unforgeable rather than merely permitted); or **(b)** those two paths stay on the **service-role client** until MV-159's grant review, which means MV-157 §G does not flip `app/api/shortlist/route.ts` and must say so. The answer is written down here, on the card that owns the grants, and it is **(a)**. **MV-157 §G's flip of `app/api/shortlist/route.ts` therefore stands** — do not revert it.
- [ ] **The UPSERT-seam trigger function carries the same revoke.** Option (a)'s `before insert or update` function on `user_program_state` and `document_status` is `security definer` with `set search_path = ''`, and its `EXECUTE` is **revoked from `public`** in the same migration. A trigger fires as the table owner regardless of who holds `EXECUTE`, so the revoke costs nothing functionally — what it removes is the ability for any signed-in client to invoke a definer function **directly** through PostgREST RPC, outside a trigger context, with a hand-built `record`. Same rule, same three-word statement, applied to all three new definer objects: `mv155_backfill_personal_cases`, `mv155_assert_case_backfill`, and this trigger function.
- [ ] `assessments` (`select` only) and `documents` (`select, delete`) need no change — stated so a reviewer sees the omission is deliberate.
- [ ] **Behaviour-preserving:** no current code path writes `case_id`, so every existing repository call still succeeds. Proven by `npm test` staying green and by the itest exercising the real upsert/insert paths for `user_program_state` and `document_status` through an **authenticated** client.
- [ ] The itest asserts the resulting grant set on the nine tables **column-granularly out of `information_schema`** (the `readGrantedWriteSurface()` idiom from `tests/integration/fixtures/tenancy.ts`), so a later migration cannot re-open the hole silently. MV-159 must preserve it — and must be told the post-MV-155 set is the baseline, not the pre-MV-155 table-level set.

**I. Types + gate**
- [ ] `lib/supabase/types.ts` regenerated; nine tables gain `case_id: string | null`. The `__InternalSupabase.PostgrestVersion: "14.5"` pin is restored by hand after regeneration (the known CLI 2.107 delta recorded on MV-150).
- [ ] **Stage 1's integration suites — `tests/integration/tenant-isolation.itest.ts` and `tests/integration/case-rls.itest.ts` — pass UNEDITED.** The gate is the *unedited* part, asserted mechanically: `git diff --stat origin/master -- tests/integration/tenant-isolation.itest.ts tests/integration/case-rls.itest.ts` shows zero changes. ## Test plan
- **New real-DB suite `tests/integration/case-backfill.itest.ts`** (`*.itest.ts`, `npm run test:integration` only), copying the **localhost hard-guard + env-gated `describe.skipIf`** and the `docker exec … psql` catalog-read idiom verbatim from `tests/integration/anon-purge.itest.ts` and `tests/integration/fixtures/tenancy.ts` (`private` and `information_schema` are not PostgREST-exposed).
  - **Structure:** all nine tables have `case_id`, `is_nullable = YES`, FK → `public.cases(id)` with `delete_rule = RESTRICT`; every index in §E exists by **coverage** (leading columns + predicate), not by name.
  - **Backfill behaviour:** seed synthetic auth users with rows across all nine tables (owner-only, mimicking pre-migration shape) → call `private.mv155_backfill_personal_cases()` → assert the report counts, one personal case per user, every owned row carrying that user's personal-case id, and `private.mv155_assert_case_backfill()` clean. Call it a **second** time → all counts zero, no row changed (idempotency).
  - **Anonymous stays case-less:** seed an `owner is null` assessment → after backfill its `case_id` is still null; `mv155_assert_case_backfill()` still clean; the MV-135 purge (`lib/assessments/purge.ts` cutoff query) still selects it, so the 3-day retention promise is unaffected.
  - **Prediction trigger, four negatives + one positive, each also as `service_role`:** null→not-null `case_id` alone succeeds; not-null→different `case_id` raises; `case_id` + `verdict` in one statement raises; `verdict` alone raises; `score_snapshot` alone raises.
  - **Personal-case uniqueness:** a second `organization_id is null` case for the same `student_user_id` is rejected (23505); a consultancy case for the same student is accepted.
  - **Per-case uniqueness bites:** a second primary assessment on one case, a second open `plan_items` row of one kind on one case, a second `documents` row of one kind on one case → each 23505; the same shapes on *different* cases → accepted.
  - **Reconciliation fails loudly:** deliberately null one owned row's `case_id`, and separately re-point one row at another user's personal case → `mv155_assert_case_backfill()` raises in both cases (proves the guard is not vacuous).
  - **PUBLIC `EXECUTE` is revoked on all three new definer objects,** asserted from `pg_proc.proacl` via the `docker exec … psql` catalog idiom (`aclexplode(proacl)` shows no `PUBLIC`/`=X/` entry) for `private.mv155_backfill_personal_cases()`, `private.mv155_assert_case_backfill()` and §H's UPSERT-seam trigger function — the same shape `case-rls.itest.ts` already runs over MV-152's twelve definer helpers, so extend that assertion rather than writing a second one. Paired with the behavioural probe that matters: an **authenticated** PostgREST client calling `rpc('mv155_backfill_personal_cases')` is refused. A catalog assertion alone would pass against a function that `authenticated` was separately granted.
  - **Grant surface, in three parts — the asymmetry is the assertion.** (1) *Negative, UPDATE only:* an **authenticated** client is rejected with `42501` when an **UPDATE** statement names `case_id`, on each of the four update-granted tables. (2) *Positive control, INSERT:* the same authenticated client **succeeds** inserting a row that carries `case_id` on each of the five insert-granted tables — this is the assertion that fails loudly if a later reviewer "tidies" `case_id` out of the INSERT lists and silently breaks MV-157's dual-write with no card owning the regression. (3) *Unchanged behaviour:* the client can still upsert `user_program_state` and toggle `document_status` exactly as today, and the `information_schema` column-grant set for the nine tables equals the expected list, column by column.
  - **The UPSERT seam is pinned by a test. §H picked (a), so (a)'s tests are required and (b)'s are the counterfactual.** Under (a), assert the definer trigger sets `case_id` from `owner` on an authenticated upsert that supplies none, and that a supplied-but-wrong `case_id` is overwritten rather than honoured. Under (b), assert `upsertProgramState` and `setObtained` still run as service-role and that an authenticated `ON CONFLICT` path naming `case_id` is rejected. A card that ships neither test has not closed the seam, it has renamed it.
- **Rehearsal (the load-bearing evidence, run once, logged):** `npx supabase db dump` from the hosted project **data-only** for `auth` + the nine `public` tables — **read-only on production, founder-gated credentials** — restored into a local stack pinned at the pre-MV-155 migration state; apply this migration alone; capture the report + reconciliation; run the full itest suite against the restored copy; then replay the rollback and re-apply to prove both directions.
- **Unit tests:** none required — no TypeScript behaviour changes in this card. `npm test` is a regression guard for the column-grant rewrite, not a proof of the migration.

CI's `integration` job is **gating**, not advisory: master is protected by an active ruleset with **no bypass** requiring `integration` + `validate` strict/up-to-date, a PR, no direct pushes and no force pushes. Locally: `npx supabase start`, then export `SUPABASE_TEST_URL`, `SUPABASE_TEST_SERVICE_ROLE_KEY` and `SUPABASE_TEST_ANON_KEY` from `npx supabase status -o env`. **The rehearsal log is a gate item too** — a green CI run against an empty local database proves nothing about a migration whose entire job is to move live rows.

## Risk notes
- **This is the first migration in the programme that mutates live user data.** Nine Auth users, 7 profiles, ~76 assessments, 74 plan items, 12 program-state rows, 6 documents, 10 predictions, 10 attempts, 19 outcome events — small enough that an in-place backfill is practical, small enough that a mistake destroys a meaningful fraction of everything the product holds. Rehearsal + rollback are not ceremony; they are the reason this card is separable from MV-156.
- **The migration is inert locally and consequential in production.** No `auth.users` exist after `db reset`, so the backfill is a no-op and the itest has to construct its own pre-migration world. A cold agent who reads "green locally" as "safe" has tested the DDL and none of the data movement.
- **`document_status` was never counted** in the plan's feasibility inspection. Its shape (`primary key (owner, kind)`) means its owner column is also a PK column — re-count it at rehearsal and do not assume it is empty.
- **`user_program_state` and `document_status` have `owner` inside their PRIMARY KEY.** Postgres forbids a nullable PK column, so **MV-156 cannot simply `alter column owner drop not null` on those two — it must replace the primary key**. Flagged here because this card's index choices must not make that harder: the new per-case uniques are separate partial indexes, not PK changes, so MV-156 is free to re-key.
- **Adding a column inherits the table-level grant.** This is the one way an additive migration can widen the client write surface, and it is why §H exists. Without it a student could `update profiles set case_id = <another case>` through the anon key the moment MV-159's policies start trusting `case_id`.
- **Narrowing the immutability trigger is a real, if bounded, widening of an invariant the codebase treats as absolute.** The alternative — drop the trigger, update, recreate, all under the `ACCESS EXCLUSIVE` lock the DDL takes — is safe against concurrent writers but leaves the *backfill statement itself* unguarded, so a mistyped `set` in the same transaction would rewrite a prediction-of-record with nothing raising. The narrowed trigger keeps the guard live during the exact operation it is protecting against. It is self-closing at MV-160 and must be restored to its unconditional body there.
- **`on delete restrict` interacts with MV-153's teardown.** The Stage-1 fixtures delete seeded cases in `afterAll`; restrict only bites if a student-owned row references them, which those fixtures never create. Verify by running the full integration suite, not by reasoning about it.
- **`cases_personal_student_idx` could collide with existing fixtures.** `tests/integration/fixtures/tenancy.ts` seeds many cases; if any run seeds two `organization_id is null` cases for one auth user, this index turns both Stage 1 suites red at the fixture, not at an assertion. Check before writing the index, and fix the fixture rather than weakening the index.
- **Account deletion leaves an orphan personal case.** `owner` is `on delete cascade` (child rows vanish) while `cases.student_user_id` is `on delete set null`, so deleting an Auth user leaves an empty, unlinked personal case. Harmless now, but it is a retention artefact — hand it to Stage 6 / MV-05's right-to-delete work rather than papering over it here.
- **Anonymous assessments must stay case-less — and there are currently ZERO of them, which changes how this is proven, not whether.** Giving an unclaimed row a case would take it out of MV-135's `owner is null` purge predicate and turn a shipped retention promise into a lie; the reconciliation function asserts `owner is null ⇒ case_id is null` precisely so a future well-meaning backfill cannot do this. **The count is stale everywhere in this carve:** the plan's "40 anonymous/unclaimed" is from 2026-07-23; a hosted capture on 2026-08-02 found 36 assessments and **0 with `owner IS NULL`** — MV-135's purge has cleared the population, which is transient by design under a 3-day TTL. The consequence is concrete and is not "update the number": **the backfill's anonymous-stays-case-less behaviour has no production data to exercise**, so it is provable only by the synthetic seed in the itest, and the rehearsal against live data cannot confirm it. Do not read a rehearsal log showing "0 anonymous rows left case-less" as evidence that the branch works; read it as evidence the branch was never entered.
- **The documents model is NOT replaced here.** `documents` and `document_status` get a `case_id` column and nothing else — no `document_requests`/`document_versions`/`document_reviews`, no mapping of status into request/review state, no `storage.objects` policy retirement, no object re-pathing. Absorbing any of that collapses the Stage 4 seam and makes this card's rollback untestable.

## Decision log
- 2026-08-02 — Card carved from Stage 2 of the revised consultancy plan (integrator session).
- 2026-08-02 — **Plan step 2 is answered: personal cases are created AT MIGRATION, not on first use.** At-migration makes the backfill a single deterministic join with an assertable completion state; first-use would leave the backfill permanently partial, force every Stage 2 repository to carry a create-or-resolve branch before MV-157 is ready to own one, and make "did the migration finish" unanswerable. The population is `auth.users` (a superset of data owners), so no owner can be missed. New users after the migration are explicitly MV-157/MV-158's create-or-resolve — the gap is stated, not filled.
- 2026-08-02 — **The prediction backfill narrows the trigger rather than dropping it.** Drop-update-recreate under one transaction is lock-safe, but it removes the guard from the one statement most likely to damage a prediction-of-record. The replacement permits exactly `case_id` null→not-null with `to_jsonb(new) - 'case_id' = to_jsonb(old) - 'case_id'`, which also covers columns added later, and is **self-closing** once MV-160 makes the column `NOT NULL`. MV-160 restores the unconditional body.
- 2026-08-02 — **The owner↔case invariant is asserted, not constrained.** It is cross-table, so no `CHECK` can express it, and a `NOT VALID` check would still enforce on new rows and break every live owner-only write before MV-157. It ships as `private.mv155_assert_case_backfill()`, called as the migration's last statement *and* by the itest, so the migration and the test share one definition. It becomes structural at MV-156 and MV-160.
- 2026-08-02 — **The backfill is a `private` function, not inline SQL.** The house rule that business logic stays in Next.js is about product behaviour; a one-shot migration mechanism is not that. Putting it in a function makes it idempotent, re-runnable during rehearsal, testable from the itest, and reportable (a `jsonb` count per table) instead of invisible.
- 2026-08-02 — **`case_id` is removed from the client write surface in the same migration that adds it,** by replacing the legacy table-level `UPDATE`/`INSERT` grants with explicit column lists (MV-152's remedy for divergences 2 and 4). A table-level grant silently extends to a new column; leaving it would hand `authenticated` the ability to re-point a row at another case the moment MV-159 starts trusting the column.
- 2026-08-02 — **Seam check: `case_id` is out of the UPDATE lists and IN the INSERT lists.** The first draft omitted it from both, which reads as consistent and is not: MV-157 moves three authenticated-client paths onto a `case_id` dual-write (`app/api/documents/status/route.ts` → `setObtained`; `app/api/shortlist/route.ts` → `upsertProgramState`, which MV-157 §G flips to the authenticated client; `captureApplication`, which already runs RLS-scoped), MV-157 §G forbids itself from adding grants, and MV-159 asserts the grant set does not change — so all three would have hit `42501` with no card responsible. Including `case_id` in the INSERT lists does not re-open the hazard §H exists to close: an INSERT creates a row rather than re-pointing one, and MV-159's `WITH CHECK` bounds which case it may name. The hazard is re-pointing, and re-pointing is UPDATE.
- 2026-08-02 — **The two PostgREST UPSERT paths are an unresolved seam assigned by name, not left to MV-157.** `upsertProgramState` and `setObtained` compile to `INSERT … ON CONFLICT DO UPDATE SET`, whose `SET` list needs `UPDATE(case_id)` — the one grant §H refuses. Resolving it in MV-157 would mean discovering it as a `42501` in production. The two candidate resolutions (a definer trigger deriving `case_id` from `owner`, preferred; or keeping those two paths on the service-role client until MV-159's grant review) are written into §H so the choice is made on the card that owns the grants, and whichever is chosen carries a test.
- 2026-08-02 — **`on delete restrict` on every `case_id` FK during the additive window.** `cascade` would let deleting a case erase a real student's data while `owner` is still authoritative; `set null` would orphan rows silently. Deletion ordering is Stage 6's explicit deliverable.
- 2026-08-02 — **Per-case uniqueness ships beside per-owner uniqueness, partial on `case_id is not null`.** The plan's rewrite table is a *destination*, not a cutover: both rule sets must hold during the dual-write window, and a non-partial unique on a nullable column would be legal but would not express the intent. The owner rules are dropped at MV-160, not here.
- 2026-08-02 — **Anonymous (owner-null) assessments stay case-less and keep purging under MV-135.** Their partial index, the purge predicate and the 3-day promise in `docs/data-retention-policy.md` all key on `owner is null`; giving them a case would quietly cancel a shipped retention commitment. The reconciliation asserts `owner is null ⇒ case_id is null` so no future backfill can do it by accident.
- 2026-08-02 — **`documents` gets a column and nothing else.** The header-plus-versions replacement, the `document_status` → request/review mapping, the dual-read/rename/drop decision and the `storage.objects` re-scoping are Stage 4, per the plan's own framing of that obstacle as a *replacement, not a column add*.
- 2026-08-02 — **Flagged for MV-156, found while reading the real schema:** `user_program_state` (PK `(owner, program_id)`) and `document_status` (PK `(owner, kind)`) carry `owner` inside their primary key, so relaxing it to nullable requires replacing the PK, not an `alter column`. This card's per-case uniques are standalone partial indexes precisely so MV-156 can re-key freely.

- 2026-08-02 — **Integrator, post-Codex-review: every new `private` definer object gets `revoke all on function … from public` in the same migration.** This card ships three (`mv155_backfill_personal_cases`, `mv155_assert_case_backfill`, §H's UPSERT-seam trigger function) and the first draft revoked none of them. Stage 1 established the discipline on all twelve of its definer helpers and asserted it in `case-rls.itest.ts`; `authenticated` already holds `USAGE` on schema `private`, so an unrevoked definer function is directly callable from a browser through PostgREST RPC. It is **latent, not exploitable today** — the backfill is idempotent and derives its writes from `owner`, so calling it achieves nothing an attacker wants. It is fixed anyway because the convention's value is that it has no exceptions, and because the exception would sit on the one function in the schema that can rewrite all nine student-owned tables. Cost: three lines and one catalog assertion extended.
- 2026-08-02 — **Integrator: the §G rollback list was incomplete and mis-ordered; corrected against matrix spec §10.1 R6.** It dropped the nine `case_id` columns but left §H's definer trigger in place on two tables that no longer had the column, left the narrowed `UPDATE`/`INSERT` column-list grants naming a dropped column, and restored the immutability-trigger body last instead of first. Also recorded: this script expires the moment MV-156 applies, because MV-156's checks and FKs make `drop column case_id` refuse — after that the only correct unwind is the stage-level reverse sweep.
- 2026-08-02 — **UPSERT seam RESOLVED by the integrator: option (a), the definer trigger.** `upsertProgramState` and `setObtained` get a `before insert or update` SECURITY DEFINER trigger on `user_program_state` and `document_status` that derives `case_id` from `owner` server-side, so the client never supplies it and no `UPDATE(case_id)` grant is needed. Chosen over (b) for four reasons: it matches the precedent already shipped and reviewed in MV-152 (`enforce_case_write_surface`, a BEFORE UPDATE trigger doing exactly this shape of server-side enforcement); it keeps both paths on the authenticated client, which is the direction the enforcement boundary requires (RLS load-bearing, service-role shrinking to an audited exception list — (b) would grow that list); it makes the dual-write **unforgeable** rather than merely permitted, closing the drift risk MV-154 names as a headline; and it is the lower-churn option, since (b) would force MV-157 to un-flip `app/api/shortlist/route.ts`. The trigger must pin `search_path = ''` like every other definer function in this codebase.
