# MV-157 — Case-aware data access: repositories and routes move off actor-equals-student onto case authorization + `case_id` (dual-write)

**Priority:** P1   **Owner:** agent
**Goal:** Move every server repository, route handler, and Server Component that reads or writes student-owned data off the `owner = actor` predicate onto a resolved `case_id` plus MV-151's `requireCasePermission` — dual-writing `owner` only where the case has an Auth user — so the codebase stops assuming the signed-in person is the student, while an existing student opening the dashboard, matches, plan, documents, checklist, guide, or outcomes sees byte-for-byte the same data as before.

### A. One case resolver, one authorization call, no actor-as-subject
- [ ] A single server-only resolver — `lib/cases/personal-case.ts`, exporting `resolvePersonalCaseId(actorUserId, db?)` and **`ensurePersonalCase(sessionUser, db?)`** — is the **only** way a personal route turns an actor into a case. It resolves `cases where student_user_id = actor and organization_id is null`; `ensurePersonalCase` is idempotent under `cases_personal_student_idx`, the partial unique index on `cases (student_user_id) where organization_id is null` that **MV-155 §A ships unconditionally**. This card asserts that index exists and **stops if it is absent** — an absent index means MV-155 did not land as specified, and re-creating it here would put the same DDL in two migrations.
- [ ] **`ensurePersonalCase` takes the verified Supabase `User` object, not an id and not a `{displayName, email}` bag.** `cases.display_name` is `not null` and `cases.email` must be the session's verified address, so the function needs identity fields it cannot get from a bare `actorUserId` — but a caller-supplied `{displayName, email}` parameter is **unprovable**: nothing in the signature or in any test can distinguish a value the caller read off `supabase.auth.getUser()` from one it read off a request body. The function therefore accepts the `User` returned by `supabase.auth.getUser()` on the server and **derives `display_name` and `email` internally** from `user.email` and `user.user_metadata`, with the precedence and the tests owned by MV-158 §A. The parameter type is the proof: there is no channel through which a client-supplied string can reach `cases.display_name` or `cases.email`, so "non-session values are ignored" is true by construction rather than by a test that can only ever assert it for the shapes it thought of. Because MV-157 and MV-158 ship in one PR (criterion J), this is the signature from the first commit — there is no widening step and no intermediate `(actorUserId, db?)` form to keep compatible.
- [ ] **Go-forward personal-case creation is wired.** MV-155 backfills cases for *existing* owners at migration time; a user who signs up afterwards must get one too. `ensurePersonalCase` is called from the non-claim sign-in seam (`lib/auth/finish-sign-in.ts`'s no-pending-claim branch), so no path can create student-owned data for an actor with no case. The claim branch of that same seam is **MV-158's**.
- [ ] Every migrated route and Server Component calls `requireCasePermission(actorUserId, caseId, <verb>)` (or the `check*` form where denial is an expected branch) **before its first read or write** — `case.read` for reads, `case.update` for mutations — and `actorUserId` comes from `supabase.auth.getUser()` on the server, never from a body, query param, header, or prop.
- [ ] **No repository resolves a case or authorizes anything.** Repos accept an already-resolved, already-authorized `caseId`; authorization lives at the entry point. A repo that calls `requireCasePermission` internally is a defect (it hides the check from the reviewer's grep and re-authorizes per query).
- [ ] The Stage 3 review-gate checklist in `lib/cases/README.md` (lines 55-79) is walked for this PR and the result recorded in Done evidence, item by item. Where an item cannot yet be satisfied (the DB half is MV-159), that is stated, not ticked.

### E. The dual-write rule (step 9), stated as code, not as discipline
- [ ] **Writes:** `case_id` is written **always**; `owner` is written **only when the case has a `student_user_id`**. Consultancy-created rows (no student user) carry `case_id` with `owner` NULL — possible only once MV-156 lands, which is why MV-156 is a hard blocker for the write half.
- [ ] **Reads:** filter on `case_id` **only**. No migrated read retains an `owner` predicate — not "as a belt", not "for the index". A residual owner filter makes every case-scoping bug invisible until MV-159 (see Risk 1).
- [ ] **`owner` is never a caller-supplied parameter next to `case_id`.** One internal writer helper derives it from the case row (`cases.student_user_id`) so a caller structurally cannot make the two disagree. A repo signature accepting both is rejected in review.
- [ ] **The dual-write DOES NOT STOP at MV-160, and that is a decision, not an omission.** MV-160's source sweep (`tests/architecture/no-actor-equals-student.test.ts`) flags any `owner:` key in an insert or upsert payload — which this card's writer helper deliberately writes on every personal-case row. It is resolved as an **explicit, justified allowlist of exactly one entry**: this writer helper, registered by path with the reason "deliberate Stage 2 dual-write; `owner` is derived from `cases.student_user_id`, never caller-supplied, and is retained as the provenance link that `app/api/account/delete` and MV-135's `owner is null` purge predicate both still read". Every **other** `owner:` payload site anywhere in `lib`/`app` fails the sweep. Removal of the dual-write is a **Stage 6** item, sequenced with dropping the `owner` columns themselves and after those two consumers are gone — not a tightening step MV-160 performs. Written on this card because this card creates the writes; asserted on MV-160 §D because that is where the detector lives.
- [ ] **The owner/case agreement has NO live database enforcement during Stage 2.** MV-155 §F is explicit: the invariant is cross-table, no `CHECK` can express it, and a `NOT VALID` check was considered and rejected. What MV-155 ships is `private.mv155_assert_case_backfill()` — an assertion **function**, called by its migration and by tests. It is a detector, not a constraint: a mismatched write is **not** rejected at write time. The single writer helper that derives `owner` from `cases.student_user_id` (criterion above) is therefore the **only** guard until MV-160, and this card proves it holds by calling `private.mv155_assert_case_backfill()` at the end of **every** mutating integration test and asserting it returns clean.

### F — Uniqueness (owned by MV-155). **This card ships NO migration.**
Plan step 7 ("add case indexes and consistency constraints") belongs to **MV-155 §E**, which already ships all six case-scoped uniqueness rules beside the legacy owner-scoped ones: `profiles unique (case_id)`, `assessments unique (case_id) where is_primary`, `plan_items unique (case_id, kind) where status = 'todo'`, `user_program_state unique (case_id, program_id)`, `documents unique (case_id, kind)`, `document_status unique (case_id, kind)`. Two cards shipping the same six indexes means one migration fails on apply or is a silent no-op, and it makes both cards' rehearsal logs and rollbacks wrong. What remains genuinely this card's is the **application side** of those rules:
- [ ] **This section is EXECUTABLE, and it was not until 2026-08-02.** MV-155 §E originally created every case-keyed unique as a **partial** index (`… where case_id is not null`). Postgres infers a partial unique index for `ON CONFLICT` **only** when the statement supplies the index predicate, and PostgREST's `on_conflict=` emits a bare column list — so every target this section moves would have raised **42P10** at runtime, and this card's only remaining job would have been undeliverable. The integrator made the four arbiter indexes **full** (`profiles (case_id)`, `user_program_state (case_id, program_id)`, `documents (case_id, kind)`, `document_status (case_id, kind)`); `NULL`s are distinct in a unique index, so the nullable window is still safe. Both directions were confirmed empirically. **Verify the four are full before writing a line of this section** (`pg_index.indpred IS NULL`, not the dossier) — if any carries a predicate, MV-155 did not land as corrected and this card is blocked, not free to work around it with a `.insert()`/`.update()` pair.
- [ ] **The `onConflict` targets move with the indexes.** Change `lib/matches/repo.ts`'s `upsert(…, { onConflict: "owner,program_id" })` to MV-155's case-scoped target, and audit the same hazard in `upsertProfile`, `upsertDocument` and `setObtained`. PostgREST's `onConflict` is an unchecked string the type system never validates (Risk 3): pointing it at an index that does not exist turns an upsert into a plain insert or a `42P10`, and pointing it at the *legacy owner* index silently keeps the write owner-scoped while every read has moved to `case_id`.
- [ ] **`upsertProgramState` and `setObtained` move their conflict target to `case_id,…` and must NOT put `case_id` in the payload.** MV-155 §H's definer trigger derives `case_id` from `owner` on those two tables precisely so the client never names the column — a payload that carries it compiles to an `ON CONFLICT DO UPDATE SET` list naming `case_id`, which needs `UPDATE(case_id)`, which Stage 2 deliberately does not grant, and fails `42501`. The conflict *target* may name `case_id` (it is an index column list, not a write); the *payload* may not. The two look alike in a `.upsert(payload, { onConflict })` call and are governed by opposite rules — state it in a comment at both call sites.
- [ ] **Every `onConflict` string in the codebase is enumerated in the PR body**, with the index each one names and whether it moved. Each is covered by a **real-DB upsert-twice test** — upsert the same logical row twice and assert one row, not two — because that is the only assertion that distinguishes "conflict target matched" from "conflict target silently missed".
- [ ] **Assert, do not create.** MV-155's six indexes are verified present at the start of this card (`\d+` or `pg_index`, not the dossier); if any is absent, stop and fix MV-155 rather than adding it here. The composite-FK targets `unique (id, owner)` → `unique (id, case_id)` on predictions/attempts/outcome_events are **MV-156's**.
- [ ] **Inherited precondition to VERIFY, not a finding to flag:** `user_program_state` (`primary key (owner, program_id)`) and `document_status` (`primary key (owner, kind)`) cannot have a nullable PK column. **MV-156 is this card's direct predecessor and already resolves it** — surrogate `id` PK plus a partial unique on the legacy pair. Confirm both tables arrive with the surrogate PK in place; if they do not, MV-156 did not land as specified and this card is blocked, not empowered to improvise.

## Risk notes
1. **The reads-move-first blind spot — highest risk of false confidence.** Until MV-159, the database still enforces the legacy owner-scoped policies on these nine tables. A read issued through the **authenticated** client with a `case_id` filter is therefore silently ANDed with `owner = auth.uid()`, so a wrong, missing, or accidentally-still-owner-scoped `case_id` filter produces correct results in Stage 2 and only fails when MV-159 removes the owner predicate — i.e. in the next card, in a different PR, with a different author. Mitigation is structural and non-negotiable: **the case-scoping assertions run through the service-role client with RLS bypassed**, so the `case_id` filter alone is what selects the rows. A test that proves case scoping while RLS is helping proves nothing.
2. **Dual-write divergence.** `owner` and `case_id` pointing at different people is the corruption this stage can produce and the hardest to detect later. There is **one** defence, not two. `owner` is derived inside one writer helper from `cases.student_user_id` and is never a caller parameter — and that is the whole of it. MV-155's `private.mv155_assert_case_backfill()` is a **detector, not a lock**: it is a function the migration and the tests call, and it rejects nothing at write time (MV-155 §F — the invariant is cross-table and no `CHECK` can express it). So the helper is load-bearing and unbacked until MV-160 makes `case_id` NOT NULL. Compensate with frequency rather than a second lock: call the assert function at the end of every mutating integration test, and treat any code path that writes `owner` outside the helper as a defect on sight.
3. **PostgREST `onConflict` is an unchecked string.** `upsertProgramState`'s `{ onConflict: "owner,program_id" }` is text the type system never validates. Changing the uniqueness target without changing the string turns an upsert into a plain insert that 23505s — or, while both index generations exist, resolves against the *legacy* index and writes the wrong row. Same class of hazard in `upsertProfile`, `upsertDocument`, and `setObtained`. Every `onConflict` in the diff is enumerated in the PR body and covered by a real-DB upsert-twice test.
4. **Keeping both index generations is safe only because a personal case is 1:1 with an owner.** If MV-155 ever produces two personal cases for one owner, the legacy and case-scoped indexes stop agreeing and writes begin failing in production for a reason that reads like an application bug. The 1:1 property is asserted directly (the partial unique index on `cases(student_user_id) where organization_id is null`), not assumed from MV-155's prose.
5. **The MV-158 interlock — a real hole if the indexes are ever swapped instead of added (MV-155 §E adds; verify that it did).** `assessments_primary_idx` is partial-unique on `(owner) where is_primary`, and a partial unique index treats NULLs as distinct. If it were *replaced* with `(case_id) where is_primary` before MV-158 teaches the claim path to set `case_id`, a claim would write `case_id = NULL` and **two primary assessments per case would become insertable** — on exactly the table with a past primary-assessment bug (`lib/assessments/claim.ts`'s demote-then-promote comment records it). Keeping both indexes closes it: the owner-scoped index still constrains any row that has an owner. **MV-160 drops the legacy index, and only after MV-158 has landed.**
6. **`user_program_state` and `document_status` arrive with a REPLACED primary key — verify it, do not re-derive it.** Both tables historically carried `owner` inside the PK (`(owner, program_id)` and `(owner, kind)`), which a `drop not null` cannot touch. **MV-156, this card's direct predecessor, already resolves it**: a surrogate `id` PK plus a partial unique on the legacy pair. The risk here is not the finding — it is assuming the legacy PK shape while writing repository code against tables whose key columns moved underneath. Read the two tables' actual PKs at the start of the card. If either is still owner-keyed, MV-156 did not land as specified and this card is blocked.
7. **Flipping a route from service-role to the authenticated client changes what it can see.** Ten `legacy-owner-scoped` paths exist precisely because `authenticated` lacks the grant (assessments SELECT-only; profiles/plan_items/documents have no INSERT). Flipping one without the grant produces a silent empty result or a 42501 in production. Only flips that need **no** grant change happen here (shortlist); the rest wait for MV-159's grant review, and each deferred entry says which grant it is waiting on.
8. **`requireCasePermission` is not a field allowlist** (MV-153 Finding 1; `lib/cases/README.md` footnote 1). On a personal case the actor is the data subject, so the whole profile surface is legitimately theirs — but `app/api/profile/section/route.ts` must keep its own payload validation, and the allowlist question is inherited, not solved, by Stage 3's consultancy mutations. Recorded on the card so Stage 3 does not read this card's silence as a solved problem.
9. **`app/(focused)/assessment/[id]/page.tsx` is a deliberate two-regime page.** Claimed rows are case-authorized; unclaimed anonymous rows keep id-as-credential. Two regimes in one file is how "knowing the id grants access" survives a refactor by accident — the branch is explicit, commented, and covered by a test on each side.
10. **This card ships no migration, and that is a hazard of its own kind.** All the DDL it depends on — the nine `case_id` columns, the six case-scoped unique indexes, the personal-case index, the assert function (MV-155), the owner relax and the PK replacements (MV-156) — arrives from predecessors. The failure mode is therefore a *drift* failure rather than an apply failure: code written against what the sibling dossiers say instead of what the database contains. Read the end state out of `pg_index` / `pg_constraint` before writing repository code, and if something is missing, fix the card that owns it. Adding "just this one index" here re-creates the duplicate-migration problem section F exists to remove.
11. **Scope creep into MV-159 is the likely failure mode.** Having moved every read to `case_id`, the obvious next keystroke is to rewrite the RLS policies to match. Do not. Policies, helper functions, and the grant review are one reviewed unit in MV-159, and splitting them across two PRs is how a policy ships without its grant.
