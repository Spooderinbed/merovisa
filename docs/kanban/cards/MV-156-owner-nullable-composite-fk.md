# MV-156 — Owner nullable on the eight NOT NULL tables + predictions→attempts→outcome_events composite-FK rebase onto the case

**Priority:** P1   **Owner:** agent
**Goal:** Make it structurally possible for a student case with **no Auth user** to hold data — relax `owner` to nullable on all eight NOT NULL student-owned tables and re-base the predictions→attempts→outcome_events ownership chain from `unique (id, owner)` onto `unique (id, case_id)` — with a compensating check that keeps the chain's ownership invariant enforced for the whole nullable window, so Stage 3 can create a consultancy case before the student exists without the schema silently dropping the constraint the chain was designed around.

## Acceptance criteria

**The eight tables — every one named, every one verified**
- [ ] `owner` is nullable on **all eight**, confirmed from `information_schema.columns.is_nullable = 'YES'` (not by reading the DDL): `public.profiles`, `public.plan_items`, `public.user_program_state`, `public.documents`, `public.document_status`, `public.program_predictions`, `public.application_attempts`, `public.outcome_events`.
- [ ] **`public.assessments` is untouched** — its `owner` has been nullable since `20260603011208` (that is how an anonymous assessment exists). It is the ninth student-owned table and deliberately not one of the eight; a diff that alters it fails this card.
- [ ] **`user_program_state` PK replaced, not "relaxed".** A PK column cannot drop NOT NULL. The table gains a surrogate `id uuid primary key default gen_random_uuid()`, the composite `primary key (owner, program_id)` is dropped, and the legacy rule survives as `user_program_state_owner_program_idx`, a **FULL** `unique index (owner, program_id)`. Verified: an authenticated duplicate `(owner, program_id)` insert still fails with `23505`; two NULL-owner rows for the same `program_id` are accepted. **CORRECTED 2026-08-03 — this criterion, spec §4.4/§4.6/§9.4/§10.1 R1 and board.json all said `where owner is not null`, and that form is unexecutable here:** `lib/matches/repo.ts:28` names this index as a bare `onConflict: "owner,program_id"` arbiter, PostgREST's bare `on_conflict=` cannot infer a PARTIAL index, and the partial form raises **42P10** on a live request for the whole MV-156 → MV-157 window. The predicate bought nothing — NULLs are distinct in a unique index, so the FULL form already permits unlimited NULL-owner rows, which is the only thing the predicate was proposed to allow. See the Decision log entry of 2026-08-03.
- [ ] **`document_status` PK replaced identically** — surrogate `id`, composite `primary key (owner, kind)` dropped, `document_status_owner_kind_idx`, a **FULL** `unique index (owner, kind)`. Same two verifications, same correction, and here it is not hypothetical: `lib/documents/status-repo.ts:36` `setObtained` is driven by `app/api/documents/status/route.ts` on the **authenticated** client **today**, so the partial form would have taken the live document checklist down with 42P10 the day this migration applied.
- [ ] No FK anywhere targets either replaced PK (verified against `pg_constraint`, not assumed) — so the swap re-points nothing.

**The composite-FK rebase (three tables)**
- [ ] `public.program_predictions` and `public.application_attempts` each carry a new `unique (id, case_id)` FK target alongside the existing `unique (id, owner)`. (Both are redundant as uniqueness — `id` is already the PK — and exist solely as composite-FK targets, exactly as `unique (id, owner)` does today.)
- [ ] `public.application_attempts` carries `foreign key (prediction_id, case_id) references public.program_predictions (id, case_id)`, and `public.outcome_events` carries `foreign key (attempt_id, case_id) references public.application_attempts (id, case_id)`.
- [ ] Each new composite FK has a **single covering index on its exact column pair** — `application_attempts (prediction_id, case_id)`, `outcome_events (attempt_id, case_id)` — per the `20260620010000` precedent, so the performance advisor reports no unindexed foreign key.
- [ ] **The legacy owner chain is retained, not dropped** — `unique (id, owner)` and the `(prediction_id, owner)` / `(attempt_id, owner)` FKs all still exist after this migration, and MV-160 drops them. Both chains are MATCH SIMPLE and each enforces exactly on the rows where its own column is non-null; together they cover every row.
- [ ] **The invariant is demonstrably restored:** inserting an `application_attempts` row whose `case_id` differs from its prediction's `case_id` is rejected (`23503`), and likewise an `outcome_events` row whose `case_id` differs from its attempt's.

**The compensating check — the thing that closes the MATCH SIMPLE hole**
- [ ] **All eight tables carry the same named, VALIDATED `check (owner is not null or case_id is not null)`**, named `<table>_ownership_axis_present` — including the three chain tables (`program_predictions_ownership_axis_present`, `application_attempts_ownership_axis_present`, `outcome_events_ownership_axis_present`). A row with **neither** axis set is rejected with `23514`; every other shape is accepted. Relaxing `owner` therefore cannot produce a row owned by nothing — invisible to every RLS policy and reachable by no cascade.
- [ ] **Why the disjunct is the correct compensating cover on the three chain tables, and not a weakening.** This card **retains** the legacy `unique (id, owner)` targets and the `(prediction_id, owner)` / `(attempt_id, owner)` FKs. So an owner-set / `case_id`-null row is still structurally enforced by the **owner** chain, and an owner-null / `case_id`-set row by the new **case** chain. The disjunct forbids exactly the one shape *no* chain covers — both axes null — which is precisely the MATCH SIMPLE hole the plan names at line 326. A flat `check (case_id is not null)` does not close that hole any better; it only also closes the live write path.
- [ ] **The pre-MV-157 write shape still succeeds — as `authenticated` and as `service_role`.** After this migration, an insert that writes only `owner` (the shape produced today by `lib/outcomes/on-apply.ts` `captureApplication`, `lib/outcomes/freeze.ts`, and `app/api/outcomes/{prediction,attempt,event}/route.ts`) still SUCCEEDS on all three chain tables. A CHECK is role-independent — `service_role` does **not** bypass it — so a `check (case_id is not null)` here takes the live outcomes write path down with `23514` for the whole MV-156 → MV-157 window, on every insert, in production.
- [ ] **Every check is named with the stable `_ownership_axis_present` suffix, and MV-160 drops ALL EIGHT. None survives into Stage 3.** This is the single agreed lifecycle, settled by the integrator 2026-08-02 after three places in this carve disagreed (an earlier version of this criterion said MV-160 drops three and five survive; this card's resume notes said all eight; MV-160 §C said three). All eight is correct and not a compromise: MV-160 sets `case_id NOT NULL` on **exactly these eight tables**, which makes the right branch of `owner is not null or case_id is not null` unconditionally true on every one of them. A check that can never fire again is not a Stage 3 safeguard — it is a constraint the next author reads as load-bearing and designs around. MV-156 §"Agent resume notes" step 4 already footer-comments the eight names in drop order; MV-154's stage criterion and MV-160 §C now both say eight. The drop order inside MV-160 is fixed: `SET NOT NULL` on the eight **first**, then the eight checks.

- [ ] The migration is **inert for existing rows apart from the two surrogate-key additions**: `git diff` shows no `UPDATE` to any of the eight, no new row-level trigger, and no touch of `private.reject_prediction_update` (that trigger is MV-155's problem, not this card's).

## Risk notes
- **The rebase is dangerous because MATCH SIMPLE makes the new constraint silently inert — this is the card's headline risk.** Postgres foreign keys default to `MATCH SIMPLE`: a multi-column FK is satisfied **without any lookup at all** if *any* referencing column is NULL. So from the moment `case_id` is nullable, `(prediction_id, case_id) → program_predictions (id, case_id)` enforces **nothing** for every row whose `case_id` is NULL. There is no error, no warning, no advisor finding: the constraint sits in `pg_constraint` looking healthy while checking nothing. What is absent is precisely the invariant `20260620000000` was written to guarantee — "structurally impossible for an attempt's owner to diverge from its prediction's owner … **no trigger**" — and it is absent during the one window where it matters most: while consultancy rows and legacy rows coexist in a half-migrated schema. The concrete failure is an `application_attempts` row pointing at another case's prediction, or an `outcome_events` row at another case's attempt: cross-case ownership divergence in the three tables that feed outcome-validation calibration, discovered later as corrupted evidence rather than as an error at write time. **Required mitigations, all four:** (1) the validated `check (owner is not null or case_id is not null)` on all three, so no row can exist with *neither* axis set — the one shape neither chain covers (a flat `check (case_id is not null)` was rejected because it also raises `23514` on every live owner-only outcomes insert, `service_role` included, until MV-157 lands); (2) **both chains retained** — this is what actually covers the owner-set / `case_id`-null rows through the whole window, and it is load-bearing, not belt-and-braces; (3) the nullable window kept short — MV-160 sets `case_id` NOT NULL first and only then may the compensating checks and the legacy owner chain be dropped, in that order; (4) the itest that *demonstrates* the hole with the check **and** the legacy FK dropped, so neither can be deleted as "redundant with the FK" by someone who has not seen what happens without them.
- **Two of the eight cannot drop NOT NULL at all, and the naive fix is worse than the error.** `user_program_state` keys `primary key (owner, program_id)` and `document_status` keys `primary key (owner, kind)`; a PK column is NOT NULL by definition and `drop not null` on it fails. An agent who "fixes" that by dropping the PK without replacing the uniqueness leaves a table where one user can hold two shortlist rows for the same program — a duplicate-state bug with no error attached to it. The PK replacement is spelled out in the acceptance criteria for exactly this reason.
- **Every owner-keyed uniqueness rule stops constraining NULL-owner rows the instant `owner` is nullable** — NULLs are distinct in a unique index. That covers `profiles.owner unique`, `documents unique (owner, kind)`, `plan_items_kind_open_idx (owner, kind) where status='todo'`, both replaced-PK partial uniques, and `program_predictions unique (owner, assessment_id, program_id, rule_version)`. The gap is bounded by card order — no consultancy row exists until Stage 3, and Stage 3 is blocked on MV-157, which re-expresses each rule on the case. **One of these is not on the plan's list** (lines 292–300 name profile, primary assessment, plan item, program state and documents, but not the predictions "one frozen run per rule version" rule): flag it to MV-157 and MV-160 rather than assuming the plan's list is exhaustive.
- **Relaxing `owner` does not open a read hole — it closes access, which is correct but will look like a bug.** Every existing policy on these tables is `(select auth.uid()) = owner`; for a NULL-owner row that predicate is NULL, so the row is invisible to every authenticated client and un-writable by them. Consultancy rows are therefore unreadable *by the counsellor who should see them* until MV-159 lands. That is the intended fail-closed interim posture. Do not add a policy here to "make Stage 3 demoable"; a policy written in this card would be written against no canonical matrix cell and is exactly the parallel-derivation failure `docs/superpowers/specs/2026-08-02-stage1-canonical-access-matrix.md` exists to prevent.
- **Cascade coverage shrinks, permanently.** `owner … on delete cascade` cleans up nothing for a NULL-owner row. That is the desired semantics (deleting a student's Auth account must not delete a consultancy case's data, and vice versa — plan line 514), but it means MV-05's right-to-delete and Stage 6's case deletion can no longer rely on the Auth cascade as their sweep. Out of scope here; recorded so it is a known consequence rather than a Stage 6 surprise.
- **This mutates live user data's schema, so reversibility is not optional** (MV-154). Seven profiles, 74 plan items, 12 user-program-state rows, 6 documents, 10 predictions, 10 attempts, 19 outcome events. Two tables get a surrogate key, which writes every row. **The rollback window is finite and must be stated on the card:** re-applying `SET NOT NULL` succeeds only while no NULL-owner row exists. Once Stage 3 writes its first consultancy row, rolling this card back means deleting consultancy data. Rehearse before, not after.
- **The types ripple is the point, not an annoyance.** `owner` flips to `string | null` across eight `Row` types and roughly 200 `owner` references in `lib/` and `app/`. A single `!` or `as string` re-asserts the exact assumption — actor equals student, owner always present — that Stage 2 exists to remove, and it does so in a place `npm run typecheck` will never complain about again. The acceptance criterion bans them.
- **Do not touch `private.reject_prediction_update` here.** DDL does not fire row-level triggers, so `drop not null`, the new uniques, the new FKs and the checks all apply without the trigger being involved — this card genuinely does not need it changed. MV-155 does need it changed, for the backfill. Two cards editing one trigger is a merge collision on the highest-consequence object in the schema.
- **Advisor discipline:** two new composite FKs mean two new required covering indexes, or `unindexed_foreign_keys` fires. The `20260620010000` migration exists solely because that was missed once already on this exact chain.

## Decision log
- 2026-08-02 — Card carved from Stage 2 of the revised consultancy plan (integrator session).
- 2026-08-02 — **The eight are enumerated on the card, and `assessments` is explicitly excluded.** The plan names the eight in prose; the card pins each to its defining migration and its exact `owner` declaration, because two of them (`user_program_state`, `document_status`) are not the simple case the prose implies. `assessments.owner` has been nullable since day one — that is what an anonymous assessment *is* — so it is the ninth student-owned table and not part of this change.
- 2026-08-02 — **`user_program_state` and `document_status` need a PK replacement, not a `drop not null`.** Both put `owner` in their PRIMARY KEY, which is NOT NULL by definition. Surrogate `id uuid` PK + a partial unique on the legacy pair `where owner is not null` preserves today's rule exactly for owner-scoped rows while letting NULL-owner rows exist. Verified no FK targets either PK, so nothing is re-pointed by the swap.
- 2026-08-02 — **The load-bearing target is swapped to the case; the legacy owner chain is retained through the window and dropped by MV-160.** A hard swap was considered and rejected: both chains are MATCH SIMPLE and each enforces exactly on rows where its own column is non-null, so dropping the owner chain now would remove enforcement from the 39 existing legacy rows for the whole MV-156→MV-160 window while buying nothing. Two coexisting redundant constraints cost two indexes and forbid no legitimate shape.
- 2026-08-02 — **A validated CHECK was chosen over `MATCH FULL` as the compensating constraint.** `MATCH FULL` would also force `case_id` non-null (the FK's other column, `prediction_id`/`attempt_id`, is NOT NULL, so all-or-nothing nullness collapses to "case_id required"). Rejected because that is precisely the shape this card must *not* impose during the window (see the entry below): a `MATCH FULL` violation would take the live owner-only outcomes insert down, would raise a foreign-key error naming the parent table rather than saying what is missing, and is unfamiliar enough that a future reader is likely to "restore" it to the default and silently re-open the hole. The CHECK states the requirement in the language of the requirement.
- 2026-08-02 — **Seam check: the compensating check on the three chain tables is the DISJUNCT, not `case_id is not null`.** The first draft shipped a validated `check (case_id is not null)` on `program_predictions` / `application_attempts` / `outcome_events`, on the argument that it is the documented path to a scan-free `SET NOT NULL` in MV-160. That argument is real and it is outweighed: a CHECK is role-independent, `service_role` does not bypass it, and every live insert on those three tables today (`lib/outcomes/on-apply.ts` `captureApplication` → `insertPrediction`/`insertAttempt`/`insertEvent`, and `app/api/outcomes/{prediction,attempt,event}/route.ts`) writes `owner` and no `case_id`. That draft therefore took the production outcomes write path down with `23514` from the moment this migration applied until MV-157 deployed — a window this card does not control. All eight tables now carry the same `check (owner is not null or case_id is not null)`, which forbids exactly the uncovered shape (both axes null) and nothing else, because both chains are retained. **Consequence accepted and handed to MV-160:** its `SET NOT NULL` on those three columns no longer has a matching validated check to skip the verification scan, so it takes a full scan under ACCESS EXCLUSIVE — negligible at 39 rows, and already flagged in MV-160's own risk note.
